# CLAUDE.md — almatn

Этот файл — техническое задание проекта для Claude Code. Читай его целиком перед началом работы. Проект: Telegram-бот **almatn**, который помогает заучивать тексты (в первую очередь — манзумы на арабском языке с пронумерованными строками) из загруженного PDF, по расписанию выдавая дневные порции и организуя их повторение по системе интервального повторения (spaced repetition).

- Пиши на TypeScript. Покрывай тестами чистую бизнес-логику (`src/core/plan`, `src/core/srs`) — это не требует БД и Telegram, тестируется быстро.

## 1. Функциональные требования

1. Пользователь отправляет боту PDF-файл с текстом, где строки пронумерованы (числами, в т.ч. арабскими цифрами ٠١٢٣٤٥٦٧٨٩).
2. Бот находит в PDF номера строк и их положение на страницах (сам текст не извлекается — см. раздел 4.1). После парсинга присылает пользователю сводку (сколько строк найдено, первая и последняя строки) для проверки корректности — пользователь должен подтвердить, что распознавание верное, прежде чем план будет построен.
3. Бот спрашивает: (а) сколько строк/объём нужно выучить (по умолчанию — весь текст, но можно указать диапазон), (б) за сколько дней.
4. Бот рассчитывает дневную норму: `units_per_day = ceil(total_units / days)`, строит план на весь срок — по одной порции (диапазону строк) на каждый день, и подтверждает план пользователю.
5. Каждый день, в заранее определённое время (по часовому поясу пользователя), бот присылает порцию текста на сегодня.
6. **Через 1 час** после отправки порции бот спрашивает (инлайн-кнопки): выучил/повторил её пользователь или нет. Ответ фиксируется, но НЕ блокирует дальнейшее расписание.
7. Каждая отправленная порция должна быть повторена по фиксированной схеме, отсчитываемой от дня её отправки: **+12 часов → +1 сутки → +3 суток → +2 недели → +1 месяц**. На каждом этапе бот присылает эту же порцию текста и спрашивает, повторил ли пользователь. После повтора "+1 месяц" порция закрывается (`completed`), новых напоминаний по ней больше нет.
8. Всё это должно работать параллельно для многих активных порций/текстов у одного и/или у многих пользователей одновременно — расписание не в памяти процесса, а в БД (см. ниже про надёжность).

## 2. Архитектура (важно соблюдать)

Слоистая структура, чтобы позже (вторым этапом, вне текущего скоупа) можно было добавить Telegram Mini App без переписывания логики:

```
almatn/
  src/
    core/
      pdf/           # парсинг PDF → массив {lineNumber, content}
      plan/           # расчёт дневной нормы и построение порций
      srs/            # расчёт цепочки дат повторов для порции
      scheduler/       # поиск "созревших" задач (due_at <= now) и их обработка
    delivery/
      bot/            # grammY-обработчики команд/сообщений/кнопок — используют только core/, никакой бизнес-логики внутри
    db/
      repositories/    # доступ к данным через Prisma, общий слой
    config/
  prisma/
    schema.prisma
  CLAUDE.md
  .env.example
  package.json
```

Правило: обработчики в `delivery/bot/` не содержат вычислений и SQL напрямую — только вызывают функции `core/…` и репозитории, и оборачивают результат в Telegram-сообщение/клавиатуру.

## 3. Технологический стек

- Node.js + TypeScript
- **grammY** — фреймворк для Telegram-бота
- **PostgreSQL + Prisma ORM**
- Планировщик: **без Redis** на старте — cron-задача (`node-cron`), раз в 1–5 минут опрашивающая таблицу `reviews`/`portions` на предмет "созревших" (`due_at <= now`) записей. Это должно быть устойчиво к перезапуску процесса — вся информация о том, когда что отправлять, хранится в БД, а не в `setTimeout`.
- PDF: **порции отправляются картинками, вырезанными из страниц PDF, а не текстом** (см. раздел 4.1 — текстовый слой реальных файлов непригоден). Нужны: извлечение слов с координатами (`pdfjs-dist` или `pdftotext -bbox` из poppler) и рендер страниц в PNG (`pdftoppm` из poppler, либо `pdfjs-dist` + `canvas`); обрезка — `sharp`. OCR не используется.
- Long polling для получения апдейтов от Telegram (без необходимости в HTTPS-домене на старте).

## 4. Модель данных (Prisma, ориентировочно)

```prisma
model User {
  id            BigInt   @id            // telegram user id
  username      String?
  timezone      String   @default("Asia/Yekaterinburg")
  dailySendTime String   @default("06:00") // "HH:mm" в часовом поясе пользователя
  createdAt     DateTime @default(now())
  texts         Text[]
}

model Text {
  id        Int      @id @default(autoincrement())
  userId    BigInt
  title     String
  sourceFile String
  totalLines Int
  createdAt DateTime @default(now())
  lines     Line[]
  plans     Plan[]
}

model Line {
  id        Int    @id @default(autoincrement())
  textId    Int
  lineNumber Int        // исправленный номер по порядку
  printedNumber Int     // как напечатано в PDF
  page      Int
  yTop      Float       // координаты в пунктах PDF
  yBottom   Float
  sectionTitle String?
  @@unique([textId, lineNumber])
}

model Plan {
  id            Int      @id @default(autoincrement())
  textId        Int
  userId        BigInt
  totalUnits    Int
  daysCount     Int
  unitsPerDay   Int
  startDate     DateTime
  status        String   @default("active") // active | completed | paused
  portions      Portion[]
}

model Portion {
  id          Int      @id @default(autoincrement())
  planId      Int
  dayIndex    Int
  scheduledDate DateTime
  lineStart   Int
  lineEnd     Int
  status      String   @default("pending") // pending | sent | learned_confirmed
  sentAt      DateTime?
  reviews     Review[]
}

model Review {
  id         Int      @id @default(autoincrement())
  portionId  Int
  stage      String   // check_1h | rep_12h | rep_1d | rep_3d | rep_2w | rep_1m
  dueAt      DateTime
  status     String   @default("pending") // pending | sent | confirmed | missed
  sentAt     DateTime?
  confirmedAt DateTime?
}
```

## 4.1. Особенности исходных PDF (проверено на реальном файле)

Эталонный файл: `samples/manzuma-fiqh.pdf` («منظومة في أحكام الفقه», 33 страницы A4, 448 бейтов). Результаты проверки:

- **Текст самих бейтов извлечь нельзя.** Арабский текст набран Type3-шрифтами со сломанной ToUnicode-таблицей: `pdftotext` отдаёт вместо строк одиночные символы-мусор, а те немногие строки, что извлекаются, идут в обратном порядке. OCR (Tesseract) на тексте с харакатами тоже ненадёжен. Поэтому бот **не хранит и не отправляет текст бейтов** — он отправляет **картинку-вырезку** из страницы, где текст выглядит точно как в оригинале, с харакатами.
- **Номера бейтов извлекаются отлично**, вместе с координатами: слова вида `(١)`, `(٢٧٥)` — арабско-индийские цифры в скобках, стоят справа от каждой строки. Их нужно переводить в обычные числа (٠١٢٣٤٥٦٧٨٩ → 0123456789).
- **Макет:** каждый бейт — одна строка из двух полустиший (правое и левое), номер справа. Между группами бейтов — заголовки разделов (`كتاب …`, `باب …`, красным крупным шрифтом). Стр. 1 — обложка без бейтов, внизу каждой страницы — номер страницы (одиночная цифра без скобок, не путать с номером бейта).
- **В самом PDF есть опечатки нумерации:** на стр. 21 бейт 286 напечатан как `(٢٧٦)`. Итог: номер 276 встречается дважды, 286 отсутствует. Парсер должен определять номер по **порядку следования** (номера идут подряд по страницам сверху вниз), а напечатанный номер использовать для сверки: если номер выбивается из последовательности, а по порядку на его месте ожидается пропущенный — исправить и сообщить пользователю в сводке («на стр. 21 бейт 286 напечатан как 276 — исправлено»).

Как это реализовать:

1. Парсинг: для каждой страницы получить слова с координатами, отобрать номера бейтов по шаблону `\(\d+\)` (после перевода цифр), выстроить последовательность, исправить аномалии, сохранить для каждого бейта `page`, `yTop`, `yBottom` (в координатах PDF). Заголовки разделов (крупные строки без номера между бейтами) по возможности сохранить как `sectionTitle` бейта — пригодится для сводки и прогресса; если определить не удалось — не блокирует.
2. Вырезка: отрендерить страницу (≈150–200 dpi), обрезать по вертикали от середины промежутка с предыдущим бейтом до середины промежутка со следующим (а не впритык к номеру — иначе срезаются харакаты), по горизонтали — всю ширину текста. Порция из нескольких бейтов на одной странице — одна картинка; порция, переходящая на другую страницу, — несколько картинок, отправляемых одним альбомом (`sendMediaGroup`), подпись — «Бейты 41–45».
3. Кэш: готовые картинки порций хранить (файл на диске или `file_id` Telegram после первой отправки — повторы отправлять по `file_id`, без повторного рендера).
4. Сводка после загрузки: сколько бейтов найдено, сколько страниц, найденные и исправленные аномалии нумерации, плюс картинка первых бейтов для визуальной проверки.
5. Если в PDF не нашлось ни одного номера в скобках — честно сообщить, что формат не поддерживается (скан или другой макет), и не строить план.

Соответственно, модель `Line` хранит не `content`, а `page`, `yTop`, `yBottom`, `printedNumber` (как напечатано), `lineNumber` (исправленный), `sectionTitle?`.

Эталонный PDF — тестовая фикстура: юнит-тест парсера должен находить на нём ровно 448 бейтов, номера 1–448 без пропусков и одну исправленную аномалию (стр. 21).

## 5. Логика SRS-цепочки

При отправке порции (`portions.status = 'sent'`, `sentAt = now`) сразу создаются записи в `Review` со следующими `dueAt`, отсчитанными от `sentAt`:

| stage | сдвиг от отправки |
|---|---|
| check_1h | +1 час |
| rep_12h | +12 часов |
| rep_1d | +1 сутки |
| rep_3d | +3 суток |
| rep_2w | +2 недели |
| rep_1m | +1 месяц |

`check_1h` — это разовая проверка "сделал ли ты сегодняшнее задание", отдельная по смыслу от долгосрочных повторов, но технически обрабатывается тем же планировщиком. После `rep_1m` цепочка по этой порции закрывается — новых `Review` не создаётся, `Portion.status → 'completed'`.

Если пользователь на каком-либо этапе отвечает "ещё не выучил/не повторил" — в MVP это только логируется (`status = 'missed'` на этом review), расписание остальных этапов не пересчитывается. Более умная адаптация (сдвиг дат при пропуске) — вне скоупа MVP, но код должен быть написан так, чтобы это можно было добавить позже, не переписывая всё (например, дата следующего этапа не должна жёстко зависеть от `dueAt` предыдущего, а вычисляться от `Portion.sentAt`).

## 6. Этапы разработки (веди по ним, этап за этапом)

1. Каркас: TS + ESLint + Prisma + подключение к Postgres + миграция по схеме выше + бот-заглушка на `/start`.
2. Приём PDF → парсинг → сохранение `Text`+`Line` → сводка пользователю с подтверждением.
3. Диалог "сколько учить / за сколько дней" → создание `Plan` + генерация всех `Portion` на весь срок.
4. Планировщик: cron-джоба, рассылка порций в назначенное время, создание `Review`-цепочки при отправке.
5. Обработка `Review`: рассылка напоминаний по `dueAt`, инлайн-кнопки подтверждения, запись ответа.
6. Юнит-тесты на `core/plan` и `core/srs`.
7. Инструкция по деплою (VPS вне РФ — см. README), systemd/pm2, бэкап БД.

## 7. Вне скоупа MVP (явно не делать сейчас)

- Telegram Mini App / веб-интерфейс (архитектура должна это допускать, но реализовывать не нужно)
- Адаптивное изменение расписания повторов при пропусках
- Многоязычный интерфейс бота (сначала — только русский текст интерфейса)
- OCR высокого качества для сканов (просто честно предупреждать пользователя)
- Оплата/подписки

## 8. Definition of Done для MVP

- Можно отправить боту PDF, получить сводку по распознанным строкам, подтвердить, задать объём и срок, получить план.
- В указанное время приходит порция на день.
- Через час приходит вопрос-проверка с кнопками.
- Через 12ч/1д/3д/2нед/1мес после отправки порции приходят повторы с тем же текстом и вопросом.
- После повтора "+1 месяц" порция больше не напоминает о себе.
- Все запланированные напоминания переживают перезапуск процесса бота (хранятся в БД, не в памяти).
- Юнит-тесты на расчёт нормы и на расчёт дат повторов — зелёные.
