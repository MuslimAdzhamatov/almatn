# CLAUDE.md — almatn

Этот файл — техническое задание проекта для Claude Code. Читай его целиком перед началом работы. Проект: Telegram-бот **almatn**, который помогает заучивать тексты из любого загруженного PDF (например, манзумы на арабском языке с пронумерованными строками), по расписанию выдавая дневные порции и организуя их повторение по системе интервального повторения (spaced repetition).

## 1. Функциональные требования

1. Пользователь отправляет боту любой PDF-файл с текстом (например, манзуму на арабском с пронумерованными строками — но номера и текстовый слой не обязательны). Можно загружать несколько текстов, в любой момент (см. раздел 4.2). Действуют лимиты (раздел 5.7).
2. Бот разбивает PDF на строки и запоминает их положение на страницах (сам текст не извлекается — см. раздел 4.1). После парсинга присылает пользователю сводку (сколько строк найдено, способ разбора, картинка первых строк) для проверки корректности — пользователь должен подтвердить, что распознавание верное, прежде чем план будет построен. Затем бот спрашивает короткое название текста (по умолчанию — имя файла).
3. Бот спрашивает: (а) что учить — по умолчанию весь файл, можно указать диапазон строк; (б) темп — на выбор пользователя: **по сроку** (количество дней, количество месяцев или конкретная дата; можно указать и дату начала) или **по количеству строк в день** (с рекомендацией 2–5 строк); (в) выходные — до двух дней в неделю. Срок может быть любым — от недели до года и больше. Месяц = 30 дней.
4. Бот рассчитывает недостающее (строк в день или дату окончания), строит календарь плана — по одной порции (диапазону строк) на рабочий день — и показывает пользователю: норму новых строк в день, ожидаемую нагрузку на повторы (в обычный день и на пике), дату окончания заучивания и дату последних повторов (+30 дней). При слишком большой нагрузке — мягкое предупреждение. Подробно — раздел 5.3.
5. Каждый рабочий день, **во время, которое выбрал сам пользователь** (любое, по его часовому поясу), бот присылает порцию на сегодня. При первом запуске бот спрашивает город/часовой пояс и время (раздел 5.4). **По одному тексту — не больше одной новой порции за плановые сутки** (раздел 5.2).
6. Под сообщением с новой порцией сразу есть кнопки «Выучил» / «Ещё учу» / «Напомнить позже». Если не нажато — одно напоминание через 2 часа (настраивается). **Новая порция не приходит, пока пользователь не отметил предыдущую и не сделал все положенные повторы** (строгий режим, раздел 5.2).
7. Каждая **выученная** порция повторяется по фиксированной схеме, отсчитываемой от момента нажатия «Выучил» (округлённого до ближайшего слота, раздел 5): **+12 часов → +1 сутки → +3 суток → +2 недели → +1 месяц (30 дней)**. Повторы **не приходят по отдельным порциям**: всё, что пора повторить в данный момент, бот объединяет в одно сообщение (см. раздел 5.1) и спрашивает один раз, повторил ли пользователь. После повтора "+1 месяц" порция закрывается (`completed`), новых напоминаний по ней больше нет.
8. Пользователь управляет всем сам: пауза (день, неделя, 2 недели, 3 недели, месяц, своя дата), смена часового пояса, времени, темпа, удаление данных; команды `/today`, `/progress`, `/texts`, `/pause`, `/settings`, `/help` (раздел 5.5).
9. Всё это должно работать параллельно для многих активных порций/текстов у одного и/или у многих пользователей одновременно — расписание не в памяти процесса, а в БД (раздел 5.6).

## 2. Архитектура (важно соблюдать)

Слоистая структура, чтобы позже (вторым этапом, вне текущего скоупа) можно было добавить Telegram Mini App без переписывания логики:

```
almatn/
  src/
    core/
      pdf/           # разбор PDF → строки с координатами {lineNumber, page, yTop, yBottom}; вырезка картинок порций
      plan/          # расчёт дневной нормы, календаря плана и нагрузки на повторы
      srs/           # слоты, цепочка дат повторов, объединение диапазонов
      scheduler/     # правила строгого режима и поиск "созревших" задач (due_at <= now)
    delivery/
      bot/           # grammY-обработчики команд/сообщений/кнопок — используют только core/, никакой бизнес-логики внутри
      api/           # появится вместе с Mini App (вне MVP)
    db/
      repositories/  # доступ к данным через Prisma, общий слой
    config/
  prisma/
    schema.prisma
  samples/           # PDF-фикстуры для тестов разбора
  CLAUDE.md
  .env.example
  package.json
```

Правило: обработчики в `delivery/bot/` не содержат вычислений и SQL напрямую — только вызывают функции `core/…` и репозитории, и оборачивают результат в Telegram-сообщение/клавиатуру. Чистые функции `core/` получают текущее время и данные параметрами (без `Date.now()` и обращений к БД внутри) — так они детерминированно тестируются.

## 3. Технологический стек

- Node.js + TypeScript; ESLint + Prettier; **vitest** — тесты
- **grammY** — фреймворк для Telegram-бота; `@grammyjs/auto-retry` (429/5xx) и троттлинг исходящих сообщений
- **PostgreSQL + Prisma ORM**; миграции — `prisma migrate dev` локально, `prisma migrate deploy` на сервере
- **luxon** — часовые пояса, слоты, переход на летнее время («+1 сутки» = то же местное время завтра, а не +24 ч)
- **zod** — проверка `.env` при старте; **pino** — структурированные логи
- `city-timezones`, `geo-tz` — определение часового пояса (раздел 5.4)
- Планировщик: **без Redis** — cron-задача (`node-cron`) раз в минуту в **том же процессе**, что и бот, опрашивает БД на предмет "созревших" (`due_at <= now`) записей. Вся информация о том, когда что отправлять, хранится в БД, а не в `setTimeout`. Защита от дублей — раздел 5.6.
- PDF: **порции отправляются картинками, вырезанными из страниц PDF, а не текстом** (см. раздел 4.1 — на текстовый слой PDF рассчитывать нельзя). Системная зависимость — **poppler**: `pdfinfo` (страницы, шифрование), `pdftotext -bbox` (слова с координатами), `pdftoppm` (рендер страниц в PNG); обрезка и анализ пикселей — `sharp`. Тяжёлый разбор выполняется вне основного потока (дочерние процессы poppler + последовательная очередь разбора), чтобы не блокировать бота и планировщик. OCR не используется.
- Long polling для получения апдейтов от Telegram (без необходимости в HTTPS-домене на старте).
- Деплой — Docker Compose (бот + Postgres; poppler ставится в образ), раздел 6.

## 4. Модель данных (Prisma, ориентировочно — финальная схема согласуется на шаге plan mode)

Ключевые решения:
- `Portion` создаётся **в момент выдачи**, а не заранее на весь план. Календарь плана и прогноз нагрузки считаются чистыми функциями из параметров `Plan` — так пауза, смена темпа, выходных и пересчёт «успеть к сроку» не требуют переписывать сотни строк.
- `Delivery` — общий журнал отправленных сообщений (новая порция, сводный повтор, напоминание о долге, напоминание про порцию, предупреждение о паузе). Уникальный ключ (пользователь, текст, вид, слот) не даёт отправить одно и то же дважды после перезапуска.
- Цепочка повторов считается от `Portion.anchorAt` (слот, к которому округлено «Выучил»), поэтому при смене пояса/времени `dueAt` пересчитываются детерминированно.

```prisma
model User {
  id            BigInt   @id            // telegram user id
  username      String?
  timezone      String            // IANA, например "Asia/Yekaterinburg"; спрашивается при первом запуске

  nightStart    String   @default("23:00") // тихие часы

  learnReminderDelayMin Int @default(120)      // через сколько минут напомнить про неотмеченную новую порцию
  pausedFrom    DateTime?                  // пауза, выставленная пользователем (или автопауза из 5.2)
  pausedUntil   DateTime?                  // null при pausedFrom != null — пауза до ручного продолжения
  lastActivityAt DateTime?                 // последнее нажатие/команда — для автопаузы

  step      String
```

## 4.1. Разбор PDF — бот должен принимать любой PDF

Пользователь может загрузить **любой PDF**: манзуму, касыду, прозу, на арабском или другом языке, с номерами строк или без, с текстовым слоем или скан. Эталонная манзума — только один из примеров. Единица заучивания в общем случае — «строка» (для манзумы это бейт).

**Главное решение: порции всегда отправляются картинками**, вырезанными из отрендеренных страниц, а не текстом. Так любой язык, харакаты, шрифты и оформление выглядят ровно как в оригинале, и не важно, есть ли в PDF нормальный текстовый слой. OCR для извлечения текста не используется.

### Что показала проверка эталонного файла

`samples/manzuma-fiqh.pdf` («منظومة في أحكام الفقه», 33 стр. A4, 448 бейтов):

- Текст бейтов из PDF не извлекается: Type3-шрифты со сломанной ToUnicode-таблицей, вместо строк мусор, редкие строки — задом наперёд. Типичная ситуация для арабских PDF — рассчитывать на текстовый слой нельзя.
- Номера бейтов `(١)…(٤٤٨)` (арабско-индийские цифры в скобках, справа от строки) извлекаются надёжно, вместе с координатами.
- Макет: бейт — одна строка из двух полустиший; между группами — заголовки разделов (`كتاب …`, `باب …`); стр. 1 — обложка; внизу — номер страницы (цифра без скобок, не номер бейта).
- В самом PDF опечатка: на стр. 21 бейт 286 напечатан как `(٢٧٦)`.
- На демо-вырезке `samples/demo_crop_1-5.png` по нижнему краю видны хвосты букв следующего бейта — граница «середина промежутка» требует уточнения по пикселям (см. «Вырезка порций»).

В `samples/` есть и другие PDF (добавлены владельцем) — их нужно изучить на этапе 3 и покрыть тестами.

### Проверки при загрузке

До разбора, с понятным сообщением пользователю в каждом случае:
- не PDF / файл повреждён; PDF с паролем; 0 страниц;
- размер больше 20 МБ — бот не может скачать такой файл через Bot API (подсказать сжать или разделить PDF);
- больше 300 страниц; лимит текстов у пользователя (раздел 5.7);
- тот же файл уже загружен (по `sha256`) — предложить открыть существующий текст.

Разбор идёт в фоне: сразу ответить «Обрабатываю…», по готовности прислать сводку. Если разбор упал — `Text.status = failed`, сообщение с предложением ручного режима.

### Стратегии разбора (пробовать по порядку)

1. **По напечатанным номерам.** Искать в текстовом слое номера строк с координатами в разных формах: `(12)`, `[12]`, `﴿12﴾`, `12.`, `12-`, `12)`; цифры западные, арабско-индийские (٠-٩) и персидские (۰-۹); номер слева или справа от строки. Номера должны идти в основном по возрастанию. Итоговый номер определяется **по порядку следования**, напечатанный — для сверки: одиночные сбои (как 276 вместо 286) исправляются и перечисляются в сводке. Номера страниц (одиночное число у края страницы без оформления) и сноски — отбрасывать.
2. **По строкам текстового слоя без номеров.** Если номеров нет, но текстовый слой есть — строками считаются группы слов с близкой вертикальной координатой; нумерует бот сам, подряд через весь документ.
3. **По изображению (скан или сломанный слой без номеров).** Отрендерить страницу, найти строки по горизонтальному профилю тёмных пикселей (полосы текста между пустыми промежутками), отбросить слишком мелкие полосы (харакаты/шум — присоединять к ближайшей строке) и слишком крупные (заголовки — помечать `sectionBreakBefore` у следующей строки). Нумерует бот сам.
4. **Ручной режим, если автоматика не справилась** или пользователь не согласен с результатом: единица = страница целиком, либо «N строк со страницы» (страница делится на равные части).

Стратегия выбирается автоматически (первая, давшая правдоподобный результат), но пользователь может переключить её в сводке. Известные трудные макеты (повёрнутые страницы, две колонки, полустишия бейта на отдельных строках) — если автоматика даёт неправдоподобный результат, предлагать ручной режим.

### Сводка и подтверждение после загрузки

Бот показывает: сколько строк найдено, на скольких страницах, какой способ разбора сработал, исправленные аномалии нумерации — и **картинку первых 3–5 строк** для визуальной проверки. Кнопки: «Всё верно», «Разобрать по-другому» (выбор стратегии/ручного режима), «Отмена», переключатель «строки / бейты». После «Всё верно» бот спрашивает название текста (кнопка «Оставить: <имя файла>»). План строится только после этого.

### Вырезка порций

- Рендер страницы ≈150–200 dpi. Вертикальные границы строки: стартовая оценка — середина промежутка с соседними строками; затем уточнение по горизонтальному профилю пикселей, чтобы не захватить хвосты букв соседних строк и заголовки разделов и не срезать харакаты. По горизонтали — вся ширина текстового блока.
- Одна картинка — `sendPhoto`; несколько (порция на нескольких страницах) — альбом `sendMediaGroup` (2–10 картинок; больше — несколько альбомов подряд). **У альбома не может быть кнопок**, поэтому кнопки всегда идут отдельным коротким текстовым сообщением сразу после картинок («Бейты 41–45 — отметь, когда выучишь»).
- Лимиты Telegram на фото: до 10 МБ, сумма ширины и высоты до 10000 px, соотношение сторон до 20:1; подпись до 1024 символов (длинные перечни диапазонов — в текстовое сообщение, не в подпись). `callback_data` до 64 байт — в кнопках только id.
- Telegram сжимает фото. На этапе 3 проверить читаемость харакатов на реальных файлах и подобрать ширину картинки; если сжатие портит текст — отправлять как документ (`sendDocument`).
- Кэш: отрендеренные страницы хранить на диске (порции и сводки режутся из них быстро); Telegram `file_id` сохранять для повторно отправляемых одинаковых вырезок (например, одна и та же порция).
- Исходный PDF хранить на диске, чтобы можно было перерезать порции.

### Хранение

Модель `Line` хранит не текст, а `page`, `yTop`, `yBottom` (координаты в пунктах PDF), `lineNumber` (итоговый), `printedNumber?` (как напечатано, если был), `sectionBreakBefore`. В `Text` — `parseStrategy`, `unitName`, `sha256`, путь к файлу.

### Тесты

Эталонный PDF — фикстура: парсер находит ровно 448 строк, номера 1–448 без пропусков, одну исправленную аномалию (стр. 21). Другие PDF из `samples/` (без номеров, сканы) — покрывать тестами соответствующих стратегий. Чистые части (поиск номеров в словах с координатами, исправление аномалий, профиль пикселей → полосы) тестировать на синтетических данных без poppler.

## 4.2. Несколько текстов у одного пользователя

- Пользователь может загрузить следующий текст в любой момент — например, выучив первую манзуму, добавить вторую. У каждого текста свой план и свои порции. Один активный план на текст; после завершения по тексту можно создать новый план (второй круг).
- Планы могут идти одновременно: новый текст можно начать, пока по предыдущему ещё идут повторы (или даже пока идёт само заучивание). При создании нового плана бот предупреждает, если он накладывается на активный, и показывает, сколько повторов уже запланировано на ближайшие дни.
- Повторы по старым текстам не прерываются при добавлении нового.
- В сообщениях всегда указывать, к какому тексту относится порция (название текста + номера строк).
- Список текстов с прогрессом — команда `/texts` (раздел 5.5).

## 5. Логика SRS-цепочки

**При отправке порции** создаётся `Portion` (`status = sent`, `sentAt = now`) и одна запись `Review` со `stage = learn_reminder`, `dueAt = sentAt + learnReminderDelayMin` (по умолчанию +2 часа).

**При нажатии «Выучил»** (`learnedAt = now`) `learn_reminder` отменяется (`cancelled`, если ещё не отправлено), вычисляется `anchorAt` — **ближайший** к `learnedAt` слот пользователя (основной или второй, в любую сторону; раздел 5.1), и создаются записи повторов:

| stage | сдвиг от `anchorAt` |
|---|---|
| rep_12h | +12 часов (следующий слот) |
| rep_1d | +1 сутки |
| rep_3d | +3 суток |
| rep_2w | +14 суток |
| rep_1m | +30 суток |

«+N суток» — тот же местный час N дней спустя (с учётом перехода на летнее время, luxon). Если слот `anchorAt + 12 ч` уже прошёл к моменту нажатия (anchor округлён назад), `rep_12h` получает `dueAt` = ближайший будущий слот.

Пока порция не отмечена «Выучил», повторов по ней нет — она только висит в долге как «выучить» (раздел 5.2).

- **«Напомнить позже»** — `learn_reminder` сдвигается на час (с учётом тихих часов).
- **«Ещё учу»** — `learn_reminder` отменяется, порция остаётся в долге, новая не приходит, пока не нажато «Выучил».
- После подтверждения `rep_1m` цепочка по порции закрывается — новых `Review` не создаётся, `Portion.status → 'completed'`. Когда все строки плана выданы и выучены — `Plan.status → learning_done`; когда все порции `completed` — `completed`.

Даты этапов считаются от `anchorAt`, а не от момента выполнения предыдущего этапа. Если повтор сделан с опозданием, следующие этапы не сдвигаются; если к моменту выполнения уже наступил и следующий этап — они просто объединяются в одну сводку (раздел 5.1). Невыполненный повтор не пропадает: он остаётся в долгах, пока пользователь его не отметит (раздел 5.2).

**Статусы `Review`:** `pending` (ещё не отправлен) → `sent` (попал в сообщение, `deliveryId` = это сообщение) → `confirmed`. Ответ «Не успел» → `missed`; такой повтор остаётся долгом и попадает в следующие напоминания (`deliveryId` перезаписывается последней отправкой). Долг = любой повтор с `dueAt <= now` и статусом не `confirmed`.

## 5.1. Сводные повторы — одно сообщение вместо нескольких

Пользователь не должен получать повторы отдельными сообщениями по каждой порции. Пример: выучил бейты 1–5 и 6–10 в разные дни, и в какой-то момент обе порции пора повторить — бот присылает **одно** сообщение «Повторить: бейты 1–10», а не два по пять.

**Слоты отправки.** У пользователя два слота в сутки: **основной** (`dailySendTime`, выбранное им время, например 06:00 или 20:00) и **второй** (+12 часов от основного). Так как `anchorAt` — всегда слот, а все сдвиги кратны 12 часам, все повторы попадают ровно в слоты: +12 ч — противоположный слот, +1 д / +3 д / +14 д / +30 д — тот же слот нужного дня.

**Тихие часы.** `dueAt` хранит логический слот. Момент фактической отправки любого сообщения (порция, сводка, напоминания, «Напомнить позже», `learn_reminder`) = время по расписанию с учётом `nightPolicy`: при `move` сообщение, попадающее в `nightStart–nightEnd`, отправляется в `nightEnd`. Это чистая функция в `src/core/srs`.

**Сборка сообщения.** В каждый слот планировщик по каждому тексту пользователя берёт повторы для отправки:
- во **второй слот** — только новые наступившие (`status = pending`, `dueAt <= now`);
- в **основной слот** — все наступившие неподтверждённые (`pending`, `sent`, `missed`) — это одновременно и сводный повтор, и напоминание о долге (раздел 5.2); если в долге есть невыученная порция — она тоже входит.

Для каждого текста:
1. объединяет диапазоны строк всех этих повторов, сливая соседние и пересекающиеся (1–5 + 6–10 → 1–10; 1–5 + 16–20 → «1–5, 16–20»);
2. отправляет картинки строк по порядку (одна — `sendPhoto`, несколько страниц — альбом, больше 10 картинок — несколько альбомов подряд), затем **одно текстовое сообщение с кнопками**: «Повторение: <название текста>, бейты 1–10, 16–20» и «Повторил» / «Не успел»;
3. создаёт `Delivery (kind = review_batch)` с уникальным ключом слота, привязывает к нему все вошедшие `Review` (`status = sent`). Ответ ставит статус всем повторам этой отправки сразу, кнопки у сообщения убираются (`editMessageReplyMarkup`).

Нажатие кнопки под **старым** сообщением подтверждает только те повторы этой отправки, которые ещё не подтверждены; повторное нажатие ничего не ломает (идемпотентно).

Для нескольких текстов у одного пользователя — по одному сводному сообщению на текст в этом слоте (у каждого текста свои картинки и свои кнопки).

**Что остаётся отдельным:** новая порция приходит своим сообщением с кнопками «Выучил» / «Ещё учу» / «Напомнить позже». Объединяются только повторы (и долг в напоминаниях, раздел 5.2).

**Если повторов накопилось много** (например, после перерыва) — всё равно одно сводное сообщение на текст; при большом числе картинок — несколько альбомов подряд, кнопки — одним сообщением в конце.

Логику объединения диапазонов, округления до ближайшего слота и применения тихих часов писать чистыми функциями в `src/core/srs` и покрыть юнит-тестами (соседние, пересекающиеся, несмежные диапазоны; «Выучил» между слотами — округление вперёд и назад; тихие часы keep/move; смена часового пояса; переход на летнее время).

## 5.2. Строгий режим: новая порция только после выполненных повторов

Цель: не дать человеку копить невыполненные повторы, пока идут новые порции (так заучивание обычно и бросают).

**Долг** по тексту — это всё, что пора было сделать и что не отмечено:
- повторы (`Review`, кроме `learn_reminder`) с `dueAt <= now` и статусом не `confirmed` (не пришедшие, отправленные без ответа, с ответом «Не успел»);
- последняя выданная новая порция, по которой не нажато «Выучил».

Долг считается **по каждому тексту отдельно**: невыполненные повторы текста A останавливают новые порции только текста A.

**Плановые сутки** — интервал от основного слота одного дня до основного слота следующего дня (по местному времени пользователя). По одному тексту выдаётся **не больше одной новой порции за плановые сутки**.

**Правило выдачи новой порции:**
- в основной слот рабочего дня: долга нет и порция в эти плановые сутки ещё не выдавалась → выдаётся следующая порция плана (`Plan.nextLine`, `unitsPerDay` строк);
- долг есть → новая порция **не выдаётся**; вместо неё приходит сводное сообщение с долгом (раздел 5.1).

**Цикл напоминаний о долге:**
1. **Конец дня** (`eveningReminderTime`, по умолчанию 21:00, настраивается). Напоминание срабатывает в эти плановые сутки, только если оно отстоит **не меньше чем на 3 часа** и от текущего, и от следующего основного слота; иначе в эти сутки пропускается. Если долг есть — одно сообщение на текст «Сегодня не выполнено: повторить бейты …; выучить бейты …» с картинками (объединёнными, как в разделе 5.1).
2. **Следующий основной слот**: если долг остался — то же сообщение повторяется, новая порция не выдаётся. Туда же добавляются повторы, которые наступили с тех пор, — всё в одном сообщении.
3. **Кнопки в сообщении о долге:** «Выучил бейты X–Y» (только если в долге есть невыученная порция; нажатие запускает цепочку повторов по разделу 5), «Повторил(а) всё» (подтверждает все повторы этого сообщения), «Не успел(а)».
4. **Закрытие долга** — когда подтверждены все наступившие повторы и выучена порция. Тогда (правило **«выдать сейчас или в слот»**, общее для первой порции плана и порции после закрытия долга):
   - сейчас рабочий день, порция в эти плановые сутки ещё не выдавалась и сейчас раньше порога (момент `eveningReminderTime` этих суток; если вечернее напоминание в эти сутки не срабатывает — за 3 часа до следующего основного слота) → новая порция приходит **сразу**;
   - иначе → в следующий основной слот рабочего дня.

**Сроки плана.** Пользователь указал срок, поэтому при задержке бот не молча сдвигает дату, а после закрытия долга (если отставание ≥ 1 порции) предлагает выбор:
- «Успеть к сроку» — оставшиеся строки перераспределяются на оставшиеся рабочие дни (норма в день растёт; бот показывает новую норму);
- «Сдвинуть срок» — норма прежняя, дата окончания переносится (бот показывает новую дату, `Plan.estimatedEndDate`).
Если до срока осталось слишком мало дней для разумной нормы (норма выросла более чем вдвое) — бот советует сдвинуть срок. Порции идут строго по порядку, пропусков не бывает. В режиме «по строкам в день» дата просто сдвигается, бот сообщает новую.

**Защита от спама:**
- долг по тексту не закрывается 3 плановых суток подряд → по этому тексту **одно сообщение в сутки** (сводка с долгом в основной слот); второй слот, вечернее напоминание и `learn_reminder` по нему не отправляются;
- пользователь **7 дней не нажал ни одной кнопки и не отправил ни одной команды** (`User.lastActivityAt`) → автоматическая пауза на уровне пользователя (те же поля, что «пока сам не продолжу», раздел 5.5) с сообщением «План на паузе. Нажми «Продолжить», когда будешь готов»; при продолжении первым делом приходит сводный повтор всего долга.

Логику «есть ли долг», «что входит в напоминание», «когда выдавать следующую порцию», «срабатывает ли вечернее напоминание» писать чистыми функциями в `src/core/` и покрыть юнит-тестами: долг закрыт до порога → порция сразу; после → в следующий основной слот; порция уже выдана в эти сутки → не выдаётся; выходной; долг не закрыт → повторное напоминание с добавлением новых повторов; вечернее напоминание при основном слоте 06:00 / 20:00 / 22:00; 3 суток долга и 7 дней без активности; пересчёт нормы «успеть к сроку».

## 5.3. Создание плана: темп, выходные, расчёт нагрузки

**Шаг 1. Что учить** — весь файл (по умолчанию) или диапазон строк.

**Шаг 2. Способ задать темп** — пользователь сам выбирает один из двух (кнопки):

- **«По сроку»** → срок задаётся одним из способов: «Количество дней» (N), «Количество месяцев» (M × 30 дней), «К дате» (`ДД.ММ.ГГГГ`, с подсказками «через месяц / 3 месяца / полгода / год»). Бот сам считает, сколько строк в день.
- **«По количеству строк в день»** → пользователь вводит число строк в день; бот сам считает дату окончания. Перед вводом бот показывает рекомендацию: «Обычно по силам 2–5 строк в день» (кнопки 2 / 3 / 5 + свой вариант).

Дата начала по умолчанию — сегодня; можно указать другую («с 1 октября»). Первая порция после «Начать» приходит по правилу «выдать сейчас или в слот» (раздел 5.2); если дата начала в будущем — в основной слот этой даты (или ближайшего рабочего дня после неё). Месяц = 30 дней. Все интервалы дат — включительно (дата начала и дата окончания — рабочие дни плана, если не выходные).

**Шаг 3. Выходные** — пользователь может выбрать **до двух дней недели** без занятий (кнопки дней недели, выбор 0–2; третий выбрать нельзя). В выходной день **не приходит только новая порция**. Повторы приходят как обычно (по своим датам и слотам, интервалы не сдвигаются), напоминания о долге по повторам — тоже. Выходной не считается пропуском и не сдвигает план сверх заложенного в расчёт. Если долг закрыт в выходной, новая порция придёт в основной слот следующего рабочего дня.

**Расчёт** (чистые функции в `src/core/plan`):
- рабочие дни = дни от даты начала до даты окончания включительно без выбранных выходных;
- режим «по сроку»: `units_per_day = ceil(total_units / рабочие_дни)`; дата окончания = указанная пользователем; если строк меньше, чем рабочих дней, — по одной строке в день, план закончится раньше срока (сообщить);
- режим «по строкам в день»: `рабочие_дни = ceil(total_units / units_per_day)`; дата окончания = дата последнего рабочего дня;
- последняя порция может быть короче;
- нагрузка на повторы: по календарю плана (с учётом выходных; предполагая, что каждая порция выучена в день выдачи) посчитать, сколько строк придётся повторять в каждый день → показать «обычно ~N строк повтора в день, на пике до ~M»;
- даты: окончание заучивания и последние повторы (дата выдачи последней порции + 30 дней).

**Предупреждение о перегрузке** (мягкое, не запрещает):
Если новых строк в день больше 10 или повтор на пике больше 50 строк (пороги — в конфиге), бот показывает окно: «Это может оказаться тяжело: каждый день N новых строк и до M строк повтора. Рекомендуем 2–5 строк в день.» Кнопки: «Уменьшить нагрузку» (вернуться к выбору темпа) / «Всё равно продолжить». Решение остаётся за пользователем.

**Подтверждение** — одно сообщение, например:
«Файл: منظومة في أحكام الفقه, бейты 1–448. Темп: 5 бейтов в день. Выходные: пятница. Заучивание закончится 30.12.2026, последние повторы — 29.01.2027. Повторение: обычно 15–25 бейтов в день. Новая порция — в 06:00, повтор через 12 часов — в 18:00, напоминание о невыполненном — в 21:00.» Кнопки: «Начать» / «Изменить темп» / «Изменить выходные» / «Изменить время».

При пересчёте из-за задержек (раздел 5.2) выходные тоже учитываются.

## 5.4. Первый запуск, часовой пояс и время отправки

1. `/start` → приветствие и вопрос о городе: пользователь пишет город (бот определяет часовой пояс по справочнику городов, например через пакет `city-timezones`) или отправляет геолокацию (часовой пояс по координатам, `geo-tz`), или выбирает часовой пояс из списка (UTC±N) кнопками. Бот показывает определённый пояс и текущее местное время для подтверждения. Город не хранится — только часовой пояс.
2. Вопрос о времени новой порции — **любое время по выбору пользователя** (кнопки с популярными вариантами + ввод `ЧЧ:ММ`).
3. Бот сразу показывает расписание, которое из этого следует: «Новая порция — в 14:00. Повтор через 12 часов — в 02:00 ночи. Остальные повторы — в 14:00. Напоминание о невыполненном — в 21:00.»
4. Если какое-то из этих времён попадает в тихие часы (по умолчанию 23:00–07:00), бот об этом говорит и предлагает выбор: «Оставить по часам» (`nightPolicy = keep`) или «Переносить ночные на утро» (`nightPolicy = move`, сообщение приходит в `nightEnd`, по умолчанию 07:00; утро можно изменить). Политика действует на все виды сообщений.
5. Если пользователь присылает PDF до завершения онбординга — бот сохраняет файл и сначала завершает онбординг, затем продолжает с разбором.
6. Всё это можно поменять позже в `/settings` (город/пояс, время, тихие часы, политика ночных, время напоминания о невыполненном). При смене времени/пояса будущие `dueAt` пересчитываются: `anchorAt` округляется к новым слотам, от него заново считаются неподтверждённые будущие этапы.

## 5.5. Управление: пауза, настройки, удаление, команды

**Пауза** (`/pause` или «Настройки → Пауза»):
- варианты длительности кнопками: 1 день, 1 неделя, 2 недели, 3 недели, 1 месяц, «до даты…», «пока сам не продолжу»;
- пауза действует на все тексты пользователя;
- во время паузы не приходит ничего: ни новых порций, ни повторов, ни напоминаний о долге; `dueAt` повторов не сдвигаются;
- при постановке бот подтверждает: «Пауза до 22.09.2026. Продолжим в 06:00 22.09»; под сообщением — «Продолжить сейчас»;
- за день до окончания паузы (если пауза дольше 2 дней) — предупреждение «Завтра продолжаем»;
- после окончания (или «Продолжить сейчас»): первым делом — одно сводное сообщение со всеми повторами, которые наступили за время паузы и до неё не были сделаны (раздел 5.1); новая порция — только после его выполнения (строгий режим 5.2);
- срок плана автоматически сдвигается на длительность паузы (в режиме «по сроку» тоже), бот сообщает новую дату окончания;
- автопауза из раздела 5.2 (7 дней без активности) использует те же поля, как «пока сам не продолжу».

**Настройки** (`/settings`), каждое изменение — с подтверждением и показом нового расписания:
- город / часовой пояс;
- время новой порции;
- тихие часы и политика ночных сообщений (по часам / на утро);
- время напоминания о невыполненном;
- через сколько напоминать про неотмеченную порцию;
- выходные (0–2 дня);
- темп по конкретному тексту: переключить «по сроку» ↔ «по строкам в день», изменить срок или число строк в день — меняется расчёт только **ещё не выданных** строк; уже выданные порции и их повторы не трогаются; бот показывает новую норму/дату и нагрузку (с тем же мягким предупреждением, что в 5.3);
- удалить один текст (план, порции, повторы, файл, кэш картинок);
- **удалить все мои данные** — двойное подтверждение («Точно удалить? Это нельзя отменить»), затем удаляются пользователь, все тексты, PDF-файлы, кэш картинок, планы и история; бот отвечает, что данные удалены и можно начать заново через `/start`.

При смене часового пояса/времени/выходных будущие `dueAt` пересчитываются по новым слотам (чистая функция + тесты).

**Команды** (зарегистрировать через `setMyCommands`, чтобы они были в меню Telegram):

| команда | что делает |
|---|---|
| `/start` | первый запуск (раздел 5.4) или приветствие и краткая сводка, если пользователь уже есть |
| `/today` | что на сегодня: новая порция (выдана / ждёт / заблокирована долгом), повторы на сегодня, долг — с кнопками открыть картинки и отметить |
| `/progress` | прогресс по каждому тексту: выучено строк из N, %, текущий темп, дата окончания, сделано/пропущено повторов, серия дней без долгов |
| `/texts` | список текстов с кратким прогрессом; у каждого — «Открыть план», «Изменить темп», «Удалить»; кнопка «Загрузить новый текст» |
| `/pause` | поставить паузу или продолжить (если пауза уже стоит) |
| `/settings` | все настройки из списка выше, включая удаление данных |
| `/help` | как пользоваться ботом: как загрузить PDF, как работают повторы и строгий режим, выходные, пауза, список команд |

Все тексты интерфейса — на русском, в одном файле (`src/delivery/bot/texts.ts`), чтобы позже было легко добавить другие языки.

## 5.6. Надёжность планировщика

- **Тик раз в минуту**, один на процесс; на время тика берётся `pg_try_advisory_lock` — если запущен второй экземпляр или предыдущий тик не закончился, новый тик пропускается.
- **Атомарные переходы статусов**: запись берётся в работу через `UPDATE … WHERE status = 'pending' … RETURNING` (или `SELECT … FOR UPDATE SKIP LOCKED`); `Delivery` с уникальным ключом (пользователь, текст, вид, слот) создаётся до отправки — повторная попытка того же слота упирается в уникальность и не шлёт дубль.
- **Ошибки отправки**: 429/5xx — повтор через `auto-retry`; иная ошибка — запись возвращается в `pending` и будет взята следующим тиком (с логом). 403 (бот заблокирован) → `User.blockedAt`, рассылка этому пользователю прекращается до следующего `/start`.
- **Догон после простоя**: при старте и на каждом тике обрабатывается всё, что созрело, но каждый пропущенный слот отправляется **один раз** (последний прошедший), а не по разу за каждый пропущенный. Если основной слот прошёл, а порция не выдана — она выдаётся по правилу «выдать сейчас или в слот» (раздел 5.2).
- **Лимиты Telegram**: троттлинг исходящих (≈ до 30 сообщений в секунду суммарно), альбомы — не чаще раза в несколько секунд одному пользователю.
- **Graceful shutdown**: на SIGTERM остановить polling и cron, дождаться окончания текущего тика, закрыть Prisma.
- **Время**: в БД всё хранится в UTC; местное время, слоты, выходные и переход на летнее время — только через luxon в чистых функциях.

## 5.7. Лимиты и доступ

- Бот **публичный** — написать ему может любой пользователь Telegram.
- PDF — не больше **20 МБ** (ограничение Bot API на скачивание файлов) и не больше **300 страниц**.
- Не больше **10 текстов** на пользователя; **один активный план** на текст.
- Повторная загрузка того же файла (одинаковый `sha256`) — не создаёт новый текст, бот предлагает открыть существующий.
- Разборы PDF выполняются последовательно (очередь), пользователю показывается его место/статус.
- Все пороги — в конфиге (`src/config`), не в коде обработчиков.
- Персональных данных хранить минимум (telegram id, username, часовой пояс; город не хранится) — сервер вне РФ, учитывать 152-ФЗ.

## 6. Этапы разработки (веди по ним, этап за этапом)

1. Каркас: TS + ESLint/Prettier + vitest + pino + zod-конфиг + Prisma + подключение к Postgres + миграция по согласованной схеме + бот-заглушка на `/start`, `setMyCommands`.
2. Первый запуск: город/часовой пояс, время, тихие часы (раздел 5.4).
3. Приём PDF → проверки и лимиты → разбор → сохранение `Text`+`Line` → сводка с картинкой, подтверждением и названием (раздел 4.1).
4. Создание плана: что учить, темп (по сроку / по строкам в день), выходные, расчёт нагрузки, предупреждение, подтверждение (раздел 5.3).
5. Планировщик: cron-джоба с защитой от дублей, выдача новых порций со строгим режимом, «Выучил» → цепочка повторов со слотами, `learn_reminder` (разделы 5, 5.2, 5.6).
6. Сводные повторы по слотам, кнопки подтверждения, напоминания о долге, защита от спама, «успеть к сроку / сдвинуть срок» (разделы 5.1, 5.2).
7. Управление: пауза, `/settings` (включая смену темпа и удаление данных), `/today`, `/progress`, `/texts`, `/help` (раздел 5.5).
8. Юнит-тесты на чистую логику `src/core` (по мере написания каждого этапа, а не в конце).
9. Деплой: Dockerfile (Node + poppler) и Docker Compose (бот + Postgres) на VPS вне РФ; `prisma migrate deploy` при старте; автоперезапуск; логи pino (опционально Sentry); ежедневный бэкап БД **и** каталога с PDF с хранением копий вне этого VPS; инструкция по деплою и восстановлению из бэкапа — в README.

## 7. Вне скоупа MVP (явно не делать сейчас)

- Telegram Mini App / веб-интерфейс (архитектура должна это допускать, но реализовывать не нужно)
- Адаптивное изменение расписания повторов при пропусках
- Многоязычный интерфейс бота (сначала — только русский текст интерфейса)
- Распознавание текста (OCR) и поиск по тексту — порции и так отправляются картинками
- Файлы больше 20 МБ (потребовали бы собственного Bot API сервера)
- Оплата/подписки

## 8. Definition of Done для MVP

- Можно отправить боту PDF, получить сводку по распознанным строкам, подтвердить, задать объём и срок, получить план.
- В указанное время приходит порция на день (картинками, кнопки — отдельным сообщением при альбоме).
- Под новой порцией есть кнопка «Выучил»; если не нажата — через 2 часа приходит одно напоминание.
- Пока есть невыполненные повторы или неотмеченная порция — новая порция по этому тексту не приходит; вечером и в основной слот приходят напоминания о долгах; после их закрытия новая порция приходит по правилам раздела 5.2; больше одной новой порции за плановые сутки не приходит.
- Через 12ч/1д/3д/14д/30д после «Выучил» (с округлением до слота) приходят повторы; все повторы одного слота по одному тексту приходят одним сообщением с объединёнными диапазонами и одним вопросом.
- После повтора "+1 месяц" порция больше не напоминает о себе.
- Все запланированные напоминания переживают перезапуск процесса бота (хранятся в БД, не в памяти), дублей после перезапуска нет.
- Пауза на выбранный срок работает: ничего не приходит, после окончания — сводный повтор, срок плана сдвинут.
- В `/settings` можно сменить часовой пояс, время, темп, выходные и удалить все данные; команды `/today`, `/progress`, `/texts`, `/pause`, `/settings`, `/help` есть в меню и работают.
- Юнит-тесты на расчёт нормы, дат повторов, слотов и правил строгого режима — зелёные; эталонный PDF разбирается в 448 строк.
