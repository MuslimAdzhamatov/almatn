# CLAUDE.md — almatn

Этот файл — техническое задание проекта для Claude Code. Читай его целиком перед началом работы. Проект: Telegram-бот **almatn**, который помогает заучивать тексты из любого загруженного PDF (например, манзумы на арабском языке с пронумерованными строками), по расписанию выдавая дневные порции и организуя их повторение по системе интервального повторения (spaced repetition).

## 0. Режим работы

- В самом начале работы над проектом (пока нет кода в `src/`) — сначала проведи ревью этого файла и `01_plan.md`: найди пробелы, противоречия и непринятые решения, дай владельцу рекомендации и вопросы, дождись ответов и внеси согласованные правки в документацию. *(Ревью проведено 16.09.2026, решения внесены в этот файл и в `01_plan.md`.)*
- Затем войди в plan mode, предложи структуру проекта и модель данных, дождись подтверждения — и только потом пиши код.
- Разработку веди небольшими итерациями (этап за этапом, см. раздел "Этапы" ниже), после каждого этапа — рабочее состояние, которое можно запустить и проверить руками.
- Пиши на TypeScript. Покрывай тестами чистую бизнес-логику (`src/core/plan`, `src/core/srs`, правила строгого режима, разбор PDF) — это не требует БД и Telegram, тестируется быстро.
- Все секреты (токен бота, строка подключения к БД) — только через `.env`, в репозиторий не коммитятся (добавь `.env` в `.gitignore`, оставь `.env.example` с плейсхолдерами).

### Git-дисциплина (обязательно, без напоминаний)

- После каждого завершённого логического шага (этап из раздела 6, значимая фича, исправление бага, обновление схемы БД, добавление тестов и т.п.) — **сразу делай `git commit` сам, не дожидаясь просьбы**. Не копи несколько несвязанных изменений в один коммит и не оставляй рабочее дерево грязным между шагами.
- Перед коммитом обязательно `git status`/`git diff`, чтобы не закоммитить `.env`, `node_modules/` или другой мусор — если что-то из этого попало в индекс, убери.
- Сообщения коммитов — на русском, в стиле Conventional Commits (`feat:`, `fix:`, `chore:`, `test:`, `docs:`, `refactor:`) и по существу: что изменилось и зачем, а не "исправления" или "обновление". Например: `feat: добавить парсинг номеров строк из PDF (западные и арабские цифры)`.
- Если после коммита остаются незакоммиченные изменения, которые логически относятся к следующему шагу — не смешивай их с текущим коммитом, дождись, пока этот шаг тоже будет завершён.
- Не пуш и не force-push без явной просьбы — только локальные коммиты по ходу работы.

### Этап 4 — создание плана (сделано)

- **`core/plan/`** (чистые функции, тесты рядом): `dates.ts` — даты плана строками `ГГГГ-ММ-ДД` (арифметика в UTC, летнее время не влияет), ввод `ДД.ММ.ГГГГ`, местная дата пользователя; `calendar.ts` — выходные (0–2, `toggleRestDay`), рабочие дни, n-й рабочий день, `nextPortionRange`, календарь порций; `pace.ts` — срок из `days:N` / `months:N` (×30) / `date:…` (N дней считаются включая дату начала), норма `ceil(единиц / рабочих дней)` и дата окончания из нормы; `load.ts` — прогноз повторов; `summary.ts` — сводка плана с флагами перегрузки; `overlap.ts` — повторы по другим открытым планам.
- **Модель прогноза нагрузки**: порция выучена в день выдачи, «Выучил» округлено к основному слоту, поэтому +12 ч попадает в те же плановые сутки, остальные этапы — через 1/3/14/30 дней; выходные повторы не сдвигают. «Обычно» — межквартильный размах дневной нагрузки за период заучивания (от первой до последней порции, включая выходные), «пик» — максимум за этот же период. Для манзумы по 5 бейтов: обычно 15–25, пик 25.
- **Сценарий `app/plans.ts`** (`flow = plan_create`): что учить (весь текст / диапазон `10-200`, «Позже») → темп («По сроку»: дни, месяцы, дата с подсказками «через месяц / 3 месяца / полгода / год» — календарные месяцы; «По количеству в день»: кнопки 2/3/5 или число) → выходные (галочки, не больше двух; по умолчанию — как в последнем открытом плане) → расчёт → при перегрузке предупреждение («Уменьшить нагрузку» / «Всё равно продолжить») → подтверждение. С подтверждения: «Начать», «Изменить темп», «Изменить выходные», **«Изменить дату начала»** (добавлено к разделу 5.3; «Сегодня» / «Завтра» / `ДД.ММ.ГГГГ`, не дальше года), «Изменить время» (меняет `User.dailySendTime` для всех текстов). Черновик и шаг — в `DialogState`, в `callback_data` — одноразовый токен диалога (`pl:<токен>:<действие>[:<значение>]`). Ошибки срока (дата раньше начала, нет рабочих дней, срок длиннее 3 лет) возвращают на ввод срока с пояснением.
- **Сохранение**: `Plan` со статусом `active`, `nextLine = lineFrom`, `estimatedEndDate` = дата последней порции, `deadlineDate` / `deadlineInput` для режима «по сроку». Второй открытый план на текст отсекает частичный индекс (Prisma `P2002` → «уже есть активный план»); проверено на локальной базе.
- **Наложение** (раздел 4.2): на подтверждении блок «⚠️ Уже идут планы …» — сколько единиц повтора по другим открытым планам в ближайшие 14 дней (уже созданные `Review` + прогноз по ещё не выданным порциям от `nextLine`, начиная с завтра) и пик вместе с новым планом.
- **Пороги** — `limits.plan` в `config/limits.ts`: больше 10 новых единиц в день или больше 50 на пике; срок до 3 лет; начало не дальше чем через год.
- **Бот**: после сохранения названия текста сразу приходит «Составим план…» (`registerTexts({ onSaved })` → `handlers/plans.ts`); экраны — `views/plans.ts` (тест проверяет, что каждый экран отрисовывается и `callback_data` ≤ 64 байт); общий `editOrReply` — `delivery/bot/edit.ts`.

  - «Выучил» → `anchorAt`, цепочка повторов, отмена ещё не отправленного напоминания и сразу `issueIfDue` (следующая порция приходит, если долг закрыт и в эти плановые сутки порции не было); статус отправки не меняется, чтобы кнопки контекста работали и после «Выучил»; «Ещё учу» отменяет напоминание; «Позже» — через 60 мин (с учётом тихих часов);
  - напоминание про неотмеченную порцию — одно, через `learnReminderDelayMin`, отдельным сообщением с кнопками отметки;
  - после последней выученной порции план → `learning_done`.
- **«⏭ Пропустить…»** (решение владельца от 16.09.2026, для любых единиц): если в порции одна единица — пропускается сразу, иначе выбор кнопками с номерами (выбор хранится битовой маской в `callback_data`, до 40 единиц; больше — только «Всю порцию»). Пропущенные единицы помечаются `skipped` навсегда (не выдаются, не показываются, не повторяются), порция пополняется следующими единицами и приходит заново как та же порция дня; старые кнопки порции снимаются (`replaced`); бот сообщает новую дату окончания (`Plan.estimatedEndDate`). Выученную порцию пропустить нельзя. Если учить больше нечего — порция удаляется, план → `learning_done`.
- **Кнопки контекста** (раздел 4.1) — под новой порцией; под сводкой после разбора — «Захватить больше» и «Ещё … ниже» (выше первой единицы ничего нет), состояние — в `callback_data` (`txctx:<текст>:<запас>:<ниже>:<действие>`).
- **Картинки** (`app/images.ts`, общий модуль вместо кода в `app/texts.ts`): кэш Telegram `file_id` (`CropCache`, ключ с версией правил вырезки `v2`), запас по бокам 3% ширины страницы, если границы строки найдены по чернилам, и белые поля вокруг каждой вырезки (по жалобе владельца от 16.09.2026: текст упирался в край).
- **Бот**: «План создан» сообщает, когда придёт первая порция, и присылает её сразу, если пора. Сообщения и кнопки — `views/learning.ts`, отправка — `delivery/bot/notifier.ts` (порт `Notifier`), кнопки — `handlers/learning.ts` (`po:<id отправки>:<действие>[:<маска>[:<индекс>]]`).

### Этап 6 — сводные повторы и долги (сделано)

- **Миграций нет** — все поля уже были в схеме.

  - `shouldAutoPause`: 7 дней без активности **и есть долг** (решение владельца от 16.09.2026; без долга пользователю может быть просто нечего нажимать);
  - `immediateEvent` — внеочередная сводка после паузы.
- **`core/plan/catchup.ts`** — `checkPace` (после закрытия долга):
  - «по сроку»: если прежняя норма укладывается в срок, дата окончания обновляется молча; если не укладывается — выбор: «Успеть к сроку» (норма = остаток / рабочие дни со следующих плановых суток до срока, с учётом выходных) или «Сдвинуть срок» (срок и дата окончания = новая дата). Если норма выросла больше чем вдвое или рабочих дней не осталось, бот советует сдвинуть срок;
  - «по количеству в день»: бот сообщает новую дату.
- **`app/reviews.ts`**:
  - сводка по каждому открытому плану (`active` и `learning_done`): `Delivery` `review_batch` (основной и второй слот) или `debt_reminder` (вечер) создаётся с ключом `dedupeKey`, потом отправка, потом `attachReviews` (статус `sent`, `deliveryId`); если отправить не удалось — запись удаляется, повтор следующим тиком;
  - сводка основного слота и вечера содержит весь долг, поэтому прежние открытые сводки текста получают статус `replaced`, их кнопки снимаются;
  - у сводки с невыученной порцией `Delivery.portionId` указывает на порцию: «Выучил …» идёт через `learning.learned`;
  - кнопки: «Повторил(а)» (в долге — «Повторил(а) всё») подтверждает `sent` и `missed` повторы отправки, «Не успел(а)» переводит `sent` → `missed`. Повторное нажатие ничего не меняет. После ответа кнопки перерисовываются по состоянию, кнопки контекста остаются (`Delivery.status` остаётся `sent`, в `answeredAt` пишется время ответа);
  - после «Повторил(а)»: `completePortions` (подтверждён `rep_1m` → `Portion.completed`, все порции закрыты и план `learning_done` → `Plan.completed`, сообщение «план завершён»), затем `issueIfDue` и проверка темпа.
- **Кнопки контекста** (`app/learning.ts`, `contextTarget`) работают и под сводкой: «Захватить больше» перерезает все диапазоны сообщения, «Ещё выше/ниже» — относительно первого и последнего диапазона. Общие помощники: `app/units.ts` (диапазоны отправки, единицы), `app/sending.ts` (результат отправки, кэш file_id, 403).
- **`app/pause.ts`** — шаг тика «автопауза»: пауза до ручного продолжения (`pausedFrom = now`, `pausedUntil = null`), сообщение с кнопкой «▶️ Продолжить» (`Delivery kind = autopause`, ключ по `lastActivityAt` — одна автопауза на период бездействия). Если сообщение не ушло, пауза снимается. «Продолжить» (`pause:resume`) снимает паузу, присылает сводку всего долга (`reviews.sendDebtNow`) и выдаёт порцию, если пора. `LearnerSettings.lastActivityAt` берёт `createdAt`, если активности ещё не было.
- **`app/tick.ts`** — общий тик под advisory lock, шаги по порядку: автопауза → сводки → порции и напоминания про порции (`learning.runDue`); ошибка шага не останавливает остальные.
- **Исходная дата окончания** записывается при выдаче первой порции (`estimatedEndDate` от фактического начала), иначе план, созданный после порога, сразу считался бы отстающим на день.
- **Бот**: `views/reviews.ts` (`rv:<id>:<ok|done|miss>`, кнопки контекста — общие `po:`), `views/pace.ts` (`pc:<план>:<c|s>`), `views/pause.ts`; обработчики `handlers/reviews.ts`, `handlers/pace.ts`, `handlers/pause.ts`; `Notifier.sendBatch` / `sendAutoPause`.

### Известные пробелы — не забыть

- «Изменить время» в диалоге создания плана пересчитывает повторы, но не задаёт вопрос о ночных сообщениях (в `/settings` задаёт).
- Прогноз наложения считает, что следующая порция другого плана будет завтра (сегодняшняя могла уже прийти); можно уточнить по `Portion.sentAt`.
- Сброс `User.blockedAt` — по любому сообщению пользователя (`users.touch`), а не только по `/start`.
- Если при замене порции после пропуска отправка не удалась, у порции не остаётся сообщения с кнопками (она по-прежнему в долге; отметить можно из напоминания) — при необходимости повторять отправку в тике.
- Две копии `npm run dev` одновременно получают 409 от Telegram (одна из них не принимает сообщения); тик защищён блокировкой, дублей порций нет.
- Одновременная загрузка одного и того же файла дважды упирается в уникальный индекс `(userId, sha256)` и даёт общую ошибку вместо «уже загружен».
- Статус `Text.failed` в схеме есть, но не используется: неудачный разбор удаляет текст (решение этапа 3a).
- Смена темпа считает остаток по диапазону `nextLine..lineTo`, включая пропущенные единицы, — норма может быть чуть выше нужной.
- Выходные в `/settings` — одни на все идущие планы (в меню показываются выходные последнего плана).
- Удаление всех данных во время разбора PDF: фоновый разбор этого текста завершится ошибкой (текста уже нет).
- Расписание в меню настроек показывает вечернее напоминание, даже если оно ближе 3 часов к основному слоту и в такие сутки не срабатывает.
- Если по неактивной сводке пропустили единицы порции («Пропустить…» под сообщением порции), кнопка «Выучил …» под этой сводкой показывает старые номера (действие верное — порция та же).
- Выбор «Успеть к сроку / Сдвинуть срок» спрашивается при каждом закрытии долга, пока план отстаёт и пользователь не выбрал вариант.
- Сводка основного слота снимает кнопки (включая кнопки контекста) у всех прежних сводок текста, даже полностью отмеченных.
- Обработчики бота (`delivery/bot/handlers`) проверяются только вручную; сценарии `app/`, `core/` и экраны `views/` покрыты юнит-тестами.
- Docker-образ и compose не собирались на машине разработки (Docker не установлен) — первая сборка будет на сервере; если сборка упадёт, чинить по логу `docker compose up --build`.
- Для арабских PDF без встроенных шрифтов рендер берёт шрифты Noto из образа — вид может отличаться от оригинала (у эталонных PDF шрифты встроены).

### Окружение и договорённости

- Локально: Postgres.app (база `almatn`; `psql` — `/Applications/Postgres.app/Contents/Versions/latest/bin/psql`), poppler через Homebrew, Node 24. Разработка — `npm run dev` (tsx watch перезапускает бота при изменениях файлов).

- Коммиты — после каждого законченного шага; push — по просьбе владельца (обычно после завершения блока или этапа). После каждого этапа — краткое резюме и инструкция для ручной проверки, затем ждать подтверждения.

## 1. Функциональные требования

1. Пользователь отправляет боту любой PDF-файл с текстом (например, манзуму на арабском с пронумерованными строками — но номера и текстовый слой не обязательны) или картинки с текстом (JPG/PNG; несколько картинок — страницы одного текста). Можно загружать несколько текстов, в любой момент (см. раздел 4.2). Действуют лимиты (раздел 5.7).
2. Бот разбивает PDF на строки и запоминает их положение на страницах (сам текст не извлекается — см. раздел 4.1). После парсинга присылает пользователю сводку (сколько строк найдено, способ разбора, картинка первых строк) для проверки корректности — пользователь должен подтвердить, что распознавание верное, прежде чем план будет построен. Затем бот спрашивает короткое название текста (по умолчанию — имя файла).
3. Бот спрашивает: (а) что учить — по умолчанию весь файл, можно указать диапазон строк; (б) темп — на выбор пользователя: **по сроку** (количество дней, количество месяцев или конкретная дата; можно указать и дату начала) или **по количеству строк в день** (с рекомендацией 2–5 строк); (в) выходные — до двух дней в неделю. Срок может быть любым — от недели до года и больше. Месяц = 30 дней.
4. Бот рассчитывает недостающее (строк в день или дату окончания), строит календарь плана — по одной порции (диапазону строк) на рабочий день — и показывает пользователю: норму новых строк в день, ожидаемую нагрузку на повторы (в обычный день и на пике), дату окончания заучивания и дату последних повторов (+30 дней). При слишком большой нагрузке — мягкое предупреждение. Подробно — раздел 5.3.
5. Каждый рабочий день, **во время, которое выбрал сам пользователь** (любое, по его часовому поясу), бот присылает порцию на сегодня. При первом запуске бот спрашивает часовой пояс (кнопки «город + смещение») и время (раздел 5.4). **По одному тексту — не больше одной новой порции за плановые сутки** (раздел 5.2).
6. Под сообщением с новой порцией сразу есть кнопки «Выучил» / «Ещё учу» / «Напомнить позже». Если не нажато — одно напоминание через 2 часа (настраивается). **Новая порция не приходит, пока пользователь не отметил предыдущую и не сделал все положенные повторы** (строгий режим, раздел 5.2).
7. Каждая **выученная** порция повторяется по фиксированной схеме, отсчитываемой от момента нажатия «Выучил» (округлённого до ближайшего слота, раздел 5): **+12 часов → +1 сутки → +3 суток → +2 недели → +1 месяц (30 дней)**. Повторы **не приходят по отдельным порциям**: всё, что пора повторить в данный момент, бот объединяет в одно сообщение (см. раздел 5.1) и спрашивает один раз, повторил ли пользователь. После повтора "+1 месяц" порция закрывается (`completed`), новых напоминаний по ней больше нет.
8. Пользователь управляет всем сам: пауза (день, неделя, 2 недели, 3 недели, месяц, своя дата), смена часового пояса, времени, темпа, удаление данных; команды `/today`, `/progress`, `/texts`, `/pause`, `/settings`, `/help` (раздел 5.5).
9. Всё это должно работать параллельно для многих активных порций/текстов у одного и/или у многих пользователей одновременно — расписание не в памяти процесса, а в БД (раздел 5.6).

## 2. Архитектура (важно соблюдать)

Слоистая структура, чтобы позже (вторым этапом, вне текущего скоупа) можно было добавить Telegram Mini App без переписывания логики:

```
almatn/
  prisma/
    schema.prisma        # источник истины для модели данных
    migrations/          # включая ручную SQL-миграцию с частичным индексом
  prisma.config.ts       # Prisma 7: путь к схеме, DATABASE_URL
  src/
    main.ts              # точка сборки: config → БД → бот → планировщик → graceful shutdown
    config/              # env.ts (zod-проверка .env), limits.ts (пороги и лимиты)
    lib/                 # logger (pino)
    core/                # ЧИСТАЯ логика: без Telegram, БД и файловой системы; now — параметром
      time/              # местное время (luxon): слоты, плановые сутки, тихие часы, выходные
      srs/               # anchorAt, цепочка этапов, слияние диапазонов, пересчёт при смене пояса
      plan/              # темп, календарь плана, прогноз нагрузки, «успеть к сроку», сдвиг на паузу
      scheduler/         # правила строгого режима: долг, что отправить в момент now, «сейчас или в слот»
      pdf/               # разбор PDF (чистые стратегии) + адаптеры poppler/sharp (poppler.ts, render.ts)
    app/                 # сценарии (use cases): репозитории + core; их же вызовет будущий delivery/api
      ports.ts           # интерфейс Notifier — планировщик не знает про Telegram
      tick.ts            # тик планировщика
    db/
      client.ts          # PrismaClient + @prisma/adapter-pg
      repositories/      # доступ к данным через Prisma
    storage/             # файлы: исходные PDF и кэш отрендеренных страниц в DATA_DIR
    delivery/
      bot/               # grammY: bot.ts, texts.ts, keyboards.ts, notifier.ts, handlers/
      api/               # появится вместе с Mini App (вне MVP)
    generated/prisma/    # сгенерированный Prisma Client (не в git)
  samples/               # PDF-фикстуры для тестов разбора
  data/                  # PDF и кэш картинок (не в git)
```

Правила:
- обработчики в `delivery/bot/` не содержат вычислений и SQL — вызывают сценарии `app/` (или репозитории для простого чтения) и оборачивают результат в Telegram-сообщение/клавиатуру;
- `core/` не импортирует grammY, Prisma, `db/`, `app/`, `delivery/` — это проверяет ESLint (`no-restricted-imports`); исключение — адаптеры `core/pdf/poppler.ts` и `core/pdf/render.ts`;
- чистые функции `core/` получают текущее время и данные параметрами (без `Date.now()` и обращений к БД внутри) — так они детерминированно тестируются;
- тесты лежат рядом с кодом (`*.test.ts`), запуск — `npm test` (vitest).

## 3. Технологический стек

- Node.js + TypeScript; ESLint + Prettier; **vitest** — тесты
- **grammY** — фреймворк для Telegram-бота; `@grammyjs/auto-retry` (429/5xx) и троттлинг исходящих сообщений
- **PostgreSQL + Prisma ORM**; миграции — `prisma migrate dev` локально, `prisma migrate deploy` на сервере
- **luxon** — часовые пояса, слоты, переход на летнее время («+1 сутки» = то же местное время завтра, а не +24 ч)
- **zod** — проверка `.env` при старте; **pino** — структурированные логи
- часовой пояс выбирается из встроенного каталога «город + смещение» (`src/core/time/zones.ts`, раздел 5.4) — внешние справочники городов и геолокация не нужны
- Планировщик: **без Redis** — cron-задача (`node-cron`) раз в минуту в **том же процессе**, что и бот, опрашивает БД на предмет "созревших" (`due_at <= now`) записей. Вся информация о том, когда что отправлять, хранится в БД, а не в `setTimeout`. Защита от дублей — раздел 5.6.
- PDF: **порции отправляются картинками, вырезанными из страниц PDF, а не текстом** (см. раздел 4.1 — на текстовый слой PDF рассчитывать нельзя). Системная зависимость — **poppler**: `pdfinfo` (страницы, шифрование), `pdftotext -bbox` (слова с координатами), `pdftoppm` (рендер страниц в PNG); обрезка и анализ пикселей — `sharp`. Тяжёлый разбор выполняется вне основного потока (дочерние процессы poppler + последовательная очередь разбора), чтобы не блокировать бота и планировщик. OCR не используется.
- Long polling для получения апдейтов от Telegram (без необходимости в HTTPS-домене на старте).
- Деплой — Docker Compose (бот + Postgres; poppler ставится в образ), раздел 6.

## 4. Модель данных

**Источник истины — [`prisma/schema.prisma`](prisma/schema.prisma)** (Prisma 7, PostgreSQL). Любое изменение модели — правка схемы + миграция `npm run db:migrate -- --name <что_изменилось>` + отдельный коммит. Ниже — ключевые решения; фрагмент схемы в конце раздела оставлен для истории и может отставать.

Ключевые решения:
- Статусы и виды — Postgres-enum; время — `DateTime` в UTC, календарные даты плана — `@db.Date`; таблицы — snake_case (`@@map`); связи с `onDelete: Cascade`, чтобы удаление текста или всех данных пользователя было одной операцией.
- `Portion` создаётся **в момент выдачи**, а не заранее на весь план. Календарь плана и прогноз нагрузки считаются чистыми функциями из параметров `Plan` — так пауза, смена темпа, выходных и пересчёт «успеть к сроку» не требуют переписывать сотни строк.
- `Delivery` — общий журнал отправленных сообщений (новая порция, сводный повтор, напоминание о долге, напоминание про порцию, окончание паузы, автопауза). Запись создаётся **до** отправки (`status = sending`) с уникальным `dedupeKey` (пользователь + текст + вид + слот) — повторная попытка того же слота после перезапуска упирается в уникальность и не шлёт дубль. Составной unique не используется: в Postgres `NULL` в `textId` не считается совпадением.
- Цепочка повторов считается от `Portion.anchorAt` (слот, к которому округлено «Выучил»), поэтому при смене пояса/времени `dueAt` пересчитываются детерминированно.
- «Один открытый план на текст» — частичный уникальный индекс `plans_one_open_per_text` в ручной SQL-миграции (Prisma не описывает частичные индексы).
- `CropCache` — Telegram `file_id` для повторно отправляемых одинаковых вырезок; `Text.parseReport` — аномалии нумерации для сводки.

## 4.1. Разбор PDF и картинок — бот принимает любой PDF или изображение текста

Пользователь может загрузить **любой PDF**: манзуму, касыду, прозу, на арабском или другом языке, с номерами строк или без, с текстовым слоем или скан. Эталонная манзума — только один из примеров. Единица заучивания в общем случае — «строка» (для манзумы это бейт); для прозы с пронумерованными абзацами — абзац (для сборника хадисов это хадис, см. «Пронумерованные абзацы»).

**Картинки (сделано).** Кроме PDF принимаются изображения текста — JPG/PNG (файлом или как фото):
- одна картинка = одна страница; альбом или несколько картинок подряд собираются в **один текст**: страницы копятся в таблице `upload_files` (переживают перезапуск), бот обновляет одно сообщение со счётчиком страниц и кнопками «Готово, это все страницы» и «Отмена» — на каждую картинку альбома отдельного ответа нет;
- по «Готово» страницы скачиваются, считается общий `sha256` по всем страницам (тот же альбом второй раз — не новый текст), файлы ложатся в `texts/<id>/source/001.jpg…`, у текста `sourceKind = images`, `filePath` — этот каталог;
- текстового слоя у картинок нет, поэтому разбор — по изображению (стратегии 3 и 5 ниже), дальше та же сводка и подтверждение; координаты хранятся в пикселях страницы (масштаб 1), поэтому вырезка порций работает тем же кодом, что и у PDF;
- Telegram сильно сжимает изображения, отправленные как фото, — харакаты могут размыться; бот принимает фото, но советует присылать картинку **файлом**;
- лимиты: до 20 МБ на файл, до 300 картинок (страниц) на текст.

**Главное решение: порции всегда отправляются картинками**, вырезанными из отрендеренных страниц, а не текстом. Так любой язык, харакаты, шрифты и оформление выглядят ровно как в оригинале, и не важно, есть ли в PDF нормальный текстовый слой. OCR для извлечения текста не используется.

### Что показала проверка эталонного файла

`samples/manzuma-fiqh.pdf` («منظومة في أحكام الفقه», 33 стр. A4, 448 бейтов):

- Текст бейтов из PDF не извлекается: Type3-шрифты со сломанной ToUnicode-таблицей, вместо строк мусор, редкие строки — задом наперёд. Типичная ситуация для арабских PDF — рассчитывать на текстовый слой нельзя.
- Номера бейтов `(١)…(٤٤٨)` (арабско-индийские цифры в скобках, справа от строки) извлекаются надёжно, вместе с координатами.
- Макет: бейт — одна строка из двух полустиший; между группами — заголовки разделов (`كتاب …`, `باب …`); стр. 1 — обложка; внизу — номер страницы (цифра без скобок, не номер бейта).
- В самом PDF опечатка: на стр. 21 бейт 286 напечатан как `(٢٧٦)`.
- На демо-вырезке `samples/demo_crop_1-5.png` по нижнему краю видны хвосты букв следующего бейта — граница «середина промежутка» требует уточнения по пикселям (см. «Вырезка порций»).

В `samples/` есть и другие PDF (добавлены владельцем) — их нужно изучить на этапе 3 и покрыть тестами.

### Проверки при загрузке

До разбора, с понятным сообщением пользователю в каждом случае:
- не PDF и не картинка / файл повреждён; PDF с паролем; 0 страниц;
- размер больше 20 МБ — бот не может скачать такой файл через Bot API (подсказать сжать или разделить PDF);
- больше 500 страниц в PDF (больше 300 картинок); лимит текстов у пользователя (раздел 5.7);
- тот же файл уже загружен (по `sha256`) — сообщить название существующего текста.

**Неподтверждённый текст.** Если пользователь присылает новый файл, а у него уже есть текст в статусе `awaiting_confirm` (разбор готов, но не нажато «Всё верно» или «Отмена»), загрузка не начинается: бот спрашивает «У вас есть неподтверждённый текст «<название>». Что сделать?» — кнопки «Продолжить с «<название>»» (заново приходит сводка этого текста с картинкой и кнопками; новый файл не загружается) и «Удалить и загрузить новый» (текст и его файлы удаляются, затем обрабатывается новый файл). Данные нового файла (`file_id`, имя, тип, размер) и одноразовый токен вопроса хранятся в `DialogState` (`flow = upload`, `step = pending_choice`), поэтому кнопки работают и после перезапуска; токен в `callback_data` делает кнопки неактуальными после ответа или после следующего вопроса. Тексты в статусе `parsing` не спрашиваются. Вопрос задаётся раньше проверки лимита текстов — удаление неподтверждённого освобождает место. Если текст успели подтвердить старыми кнопками, «Удалить и загрузить новый» его не трогает и просто загружает файл.

Разбор идёт в фоновой последовательной очереди: сразу ответить «Файл получен, разбираю…» (с местом в очереди, если она занята), по готовности прислать сводку. Статус `parsing` хранится в БД — разборы, прерванные перезапуском, при старте запускаются заново. Если разбор упал — текст и его файлы **удаляются** (неразобранный текст не должен занимать место в лимите текстов), пользователь получает понятную причину («защищён паролем», «не удалось разобрать»).

### Стратегии разбора (пробовать по порядку)

1. **По напечатанным номерам** *(этап 3a)*. Искать в текстовом слое номера строк с координатами в разных формах: `(12)`, `[12]`, `﴿12﴾`, `12.`, `12-`, `12)`; цифры западные, арабско-индийские (٠-٩) и персидские (۰-۹); номер слева или справа от строки; номер, разбитый текстовым слоем на части («(», «١», «)»), склеивается. Колонка номеров — окно наибольшей плотности по центру, правому или левому краю номера (у номеров, выровненных по правому краю, центр «гуляет» с числом цифр). Номера должны идти в основном по возрастанию. Итоговый номер определяется **по порядку следования**, напечатанный — для сверки:
   - одиночная опечатка (276 вместо 286) исправляется и перечисляется в сводке;
   - номер страницы или сноски, попавший в колонку номеров, пропускается, если последовательность сразу продолжается (если лишним был предыдущий номер — например, сноска «١» до начала текста, — строка заменяется);
   - строка без распознанного номера восстанавливается по положению, если на её место есть место; пропуск в нумерации без пропуска строки — строки нумеруются по порядку;
   - если нумерация начинается заново (текст, затем разбор с повтором бейтов, как в `sollam_wosol.pdf`), берётся самая длинная последовательность, диапазон страниц показывается в сводке.
2. **По строкам текстового слоя без номеров** *(сделано, `core/pdf/textlines.ts`)*. Если номеров нет, но текстовый слой есть — строка собирается из слов, вертикальные интервалы которых перекрываются (огласовки идут в текстовом слое отдельными «словами» со смещением); нумерует бот сам, подряд через весь документ. Колонтитул отсекается по двум признакам сразу: строка стоит у края страницы (12% высоты) **и** узкая (меньше половины обычной ширины) **и** повторяется на той же высоте на половине страниц — иначе под правило попадала бы первая строка каждой страницы. Обложка, титул и колофон отбрасываются как страницы, где строк заметно меньше обычного (берётся самый длинный отрезок «полных» страниц). Строка заметно выше обычной — заголовок раздела: он не считается единицей, а становится фрагментом `heading` следующей за ним единицы. Если «заголовками» выглядит больше трети строк, текстовый слой считается сломанным (как в `متن عمدة الاحكام.pdf`) и стратегия не применяется — такой файл пойдёт в разбор по изображению. Границы вырезки уточняются по пикселям тем же кодом, что и у разбора по номерам.
3. **По изображению** *(сделано, `core/pdf/imagelines.ts`; сканы и PDF со сломанным текстовым слоем)*. Страница рендерится в оттенках серого (100 dpi), строки ищутся по горизонтальному профилю тёмных пикселей — полосы текста между пустыми промежутками. Дальше полосы разбираются по видам: сплошная линия (рамка колонтитула, черта над сносками) — у неё самая тёмная строка пикселей занимает больше 0,6 ширины страницы либо полоса тонкая и темнее 0,35 ширины (у настоящей строки текста максимум около трети ширины, буквы не идут подряд); мелкая полоса (харакаты, точки) присоединяется к ближайшей строке; слипшиеся строки (полоса заметно выше обычной) делятся на равные части по самому светлому месту профиля; узкая полоса (уже 0,65 обычной ширины строки) — заголовок раздела, он становится фрагментом `heading` следующей единицы. Колонтитулы отсекаются так же, как в стратегии 2: узкая полоса у края страницы, повторяющаяся примерно на той же высоте на половине страниц. Обычная высота и ширина строки считаются по всему документу, поэтому классификация идёт вторым проходом — страницы рендерятся частями, от каждой остаются только профиль и полосы (несколько килобайт), а картинки сразу удаляются. Обложка и пустые страницы отбрасываются по числу строк текста, но отрезок расширяется на соседние страницы, где есть хоть одна строка, — иначе теряется концовка книги. Нумерует бот сам.
4. **Абзацы** *(сделано, `core/pdf/paragraphs.ts`)* — проза, где единица заучивания — абзац целиком (в сборнике хадисов это хадис); единица называется «абзацы» и переключается в сводке на «хадисы». **Номера абзацев из PDF не берутся** (решение владельца от 16.09.2026): в `متن عمدة الاحكام.pdf` текстовый слой сломан, а на изображении номер не отделяется от текста — пробел после «٤ –» такой же, как между словами (1–2 пикселя при 100 dpi), и без OCR его не найти. Поэтому абзацы нумеруются по порядку, сверки с напечатанным номером нет. Границы абзаца — по вёрстке: абзац заканчивается **короткой строкой** (строки выключены по обоим краям, не дотягивает до края только последняя). Полная ширина строки и границы набора считаются по высокому квантилю, а не по медиане: в прозе с короткими абзацами половина строк короткие. Заголовок раздела отличается от короткой строки абзаца **отступами с обеих сторон** (короткая строка прижата к краю) и становится фрагментом `heading` следующего абзаца. Сноски отсекаются по хвосту страницы, набранному мельче основного текста; колонтитулы — как в стратегиях 2 и 3. Абзац может занимать несколько строк и страниц — тогда у него по фрагменту на страницу. Если абзацы не выделяются (в стихах короткой оказывается не каждая строка, а почти ни одной), стратегия не применяется и текст разбирается по строкам.
5. **Ручной режим** *(сделано)*: единица = страница целиком либо «N строк со страницы» — страница делится на равные полосы (до 30, `limits.pdf.maxLinesPerPage`).

Стратегия выбирается автоматически (первая, давшая правдоподобный результат), но пользователь может переключить её в сводке: сейчас это номера → строки текстового слоя → строки по изображению → постранично. Известные трудные макеты (повёрнутые страницы, две колонки, полустишия бейта на отдельных строках) — если автоматика даёт неправдоподобный результат, предлагать ручной режим.

### Сводка и подтверждение после загрузки

Бот показывает: сколько строк найдено и на каких страницах, какой способ разбора сработал, исправленные аномалии нумерации (до 10, дальше «…и ещё N») — и **картинку первых 5 строк** (при постраничном разборе — первую страницу). Кнопки: «Всё верно»; «Называть «бейты» / «строки»» (для прозы — «хадисы» / «абзацы»); «⚙️ Разобрать по-другому»; «Отмена» (текст и файл удаляются).

**«Разобрать по-другому»** (сделано) — меню, где пользователь сам выбирает: стратегию (по номерам строк, по строкам текста, по абзацам, по строкам на картинке, постранично), «N строк со страницы…» (бот спрашивает число) и «Выбрать страницы…» (бот спрашивает диапазон вида `3-240`; одно число — с него до конца). Выбор хранится у текста в `parseRequest`, поэтому переразбор повторяется и после перезапуска бота, а диапазон страниц сохраняется при смене стратегии. Этим же решаются случаи, которые автоматика не берёт: хвост нумерации в `sollam_wosol.pdf` (бейты 291–324 на стр. 79–89), концевая страница манзумы, пустые страницы-разделители в `0200Mutoon.pdf`. После «Всё верно» бот спрашивает название текста — текстом или кнопкой «Оставить «<имя файла>»» (по умолчанию имя файла без `.pdf`). План строится только после этого. Старые кнопки и чужие тексты не срабатывают («Эта кнопка уже неактуальна»).

### Вырезка порций

- Рендер страницы ≈150–200 dpi (анализ строк — 100 dpi в оттенках серого, картинки для пользователя — 200 dpi). Вертикальные границы строки: стартовая оценка — середина промежутка с соседними строками; затем уточнение по горизонтальному профилю пикселей, чтобы не захватить хвосты букв соседних строк и заголовки разделов и не срезать харакаты. По горизонтали — вся ширина текстового блока.
- **Заголовок раздела** перед первой единицей порции входит в её картинку: вырезка расширяется вверх до заголовка (а если он остался внизу предыдущей страницы — приходит отдельной картинкой перед строками). Заголовок внутри порции попадает в картинку сам собой. Заголовок не считается единицей: порция из 5 строк остаётся порцией из 5 строк. Подряд идущие заголовки (`كتاب`, затем `باب`) входят оба. Колонтитул заголовком не считается — он повторяется на каждой странице на одном месте. В сводных повторах заголовок показывается так же, перед началом каждого диапазона.
- Одна картинка — `sendPhoto`; несколько (порция на нескольких страницах) — альбом `sendMediaGroup` (2–10 картинок; больше — несколько альбомов подряд). **У альбома не может быть кнопок**, поэтому кнопки всегда идут отдельным коротким текстовым сообщением сразу после картинок («Бейты 41–45 — отметь, когда выучишь»).
- Лимиты Telegram на фото: до 10 МБ, сумма ширины и высоты до 10000 px, соотношение сторон до 20:1 (слишком узкая полоса дополняется белыми полями); подпись до 1024 символов (длинные перечни диапазонов — в текстовое сообщение, не в подпись). `callback_data` до 64 байт — в кнопках только id.
- Telegram сжимает фото. **Проверено на эталонной манзуме (200 dpi): харакаты после сжатия читаются**, поэтому порции отправляются фото (`sendPhoto`). Если на других текстах сжатие начнёт портить текст — отправлять как документ (`sendDocument`).
- Кэш: отрендеренные страницы хранить на диске в `DATA_DIR/texts/<id>/pages` (порции и сводки режутся из них быстро); Telegram `file_id` сохранять для повторно отправляемых одинаковых вырезок (например, одна и та же порция).
- Исходный файл хранить на диске (`DATA_DIR/texts/<id>/source.pdf`), чтобы можно было перерезать порции.

### Показать больше контекста (этап 5)

Автоматика иногда режет неточно: обрезает харакаты и хвосты букв, обрывает фразу, которая продолжается на следующей строке, или единица оказывается выделена не полностью. Пользователь должен уметь достать недостающее сам, не переразбирая текст. Под каждым сообщением с картинками (новая порция, сводный повтор, напоминание о долге, а также сводка после разбора) — дополнительные кнопки (сделано: для новой порции и сводки после разбора — на этапе 5, для сводного повтора и напоминания о долге — на этапе 6):

- **«🔍 Захватить больше»** — те же единицы, но картинка перерезается с вертикальным запасом: по 40% высоты строки сверху и снизу, каждое следующее нажатие добавляет ещё столько же, не больше трёх раз и не вылезая за края страницы. Состав единиц при этом **не меняется** — это только картинка.
- **«⬆️ Ещё выше» и «⬇️ Ещё ниже»** — присылают соседнюю единицу (предыдущую перед первой или следующую после последней) отдельной картинкой с подписью. Каждое нажатие добавляет ещё одну, не больше пяти в каждую сторону. На краях текста кнопка отвечает «выше/ниже ничего нет».

Правила:
- Названия кнопок зависят от единицы текста: «Ещё строку», «Ещё бейт», «Ещё хадис», «Ещё абзац», «Ещё страницу».
- Дополнительные картинки приходят **новыми сообщениями**; исходное сообщение с кнопками не трогается (в альбоме медиа не заменить).
- Это **только просмотр**: границы порции, `Portion.lineStart/lineEnd`, цепочка повторов и ответы «Выучил» / «Повторил» не меняются.
- Сколько уже добавлено, хранится у отправки (`Delivery`: запас вырезки и число добавленных единиц вверх и вниз) — кнопки продолжают работать после перезапуска бота. Для сводки после разбора состояние в базе не хранится: запас и число досланных единиц передаются в `callback_data`; кнопки «Ещё выше» под сводкой нет — она начинается с первой единицы.
- Кэш вырезок (`CropCache`) работает как есть: ключ уже включает границы, поэтому расширенная картинка кэшируется отдельно. При изменении правил вырезки повышается версия ключа (`CROP_STYLE_VERSION`).

### Пропустить единицу (этап 5)

Под новой порцией — кнопка «⏭ Пропустить…» для любых единиц: обложка, колофон, заголовок или страница, которую учить не нужно. Пропущенная единица не выдаётся, не показывается и не повторяется; порция сразу пополняется следующими единицами и приходит заново как та же порция дня, бот сообщает новую дату окончания. Подробности — в разделе «Статус проекта», этап 5.

### Хранение

Модель `Line` — единица заучивания (строка, бейт, хадис, абзац): `lineNumber` (итоговый), `printedNumber?` (как напечатано, если был), `page` (страница первого фрагмента), `sectionBreakBefore`. Текст не хранится. Что вырезать со страницы, хранит `LineFragment`: `seq`, `kind` (`text` | `heading`), `page`, `yTop`, `yBottom`, `xLeft?`, `xRight?` (пункты PDF; для текстов из картинок — пиксели страницы). У обычной строки один фрагмент; у абзаца на развороте — по фрагменту на страницу; заголовок раздела перед единицей — отдельный фрагмент `heading`. В `Text` — `parseStrategy`, `unitName` (`lines` | `bayts` | `hadiths` | `paragraphs`), `sourceKind` (`pdf` | `images`; для картинок `filePath` — каталог со страницами), `sha256`, `parseReport` (диапазон страниц, аномалии нумерации, причина постраничного разбора). `UploadFile` хранит присланные файлы, которые ещё не стали текстом (страницы альбома до кнопки «Готово», файл до конца настройки расписания): только `file_id` и данные Telegram, сам файл не скачан.

### Тесты

Эталонный PDF — фикстура: парсер находит ровно 448 строк, номера 1–448 без пропусков, одну исправленную аномалию (стр. 21). `sollam_wosol.pdf` — основной текст, бейты 1–290 на стр. 8–28 (разбор с повтором бейтов не мешает); `المقدمة الجزرية.pdf` (скан) — номеров в текстовом слое нет, в 3b — строки по изображению; `متن عمدة الاحكام.pdf` — в 3b хадисы по номерам абзацев. Тесты на реальных PDF запускаются через poppler и пропускаются, если он не установлен. Чистые части (поиск номеров в словах с координатами, исправление аномалий, профиль пикселей → полосы) тестировать на синтетических данных без poppler.

## 4.2. Несколько текстов у одного пользователя

- Пользователь может загрузить следующий текст в любой момент — например, выучив первую манзуму, добавить вторую. У каждого текста свой план и свои порции. Один активный план на текст; после завершения по тексту можно создать новый план (второй круг).
- Планы могут идти одновременно: новый текст можно начать, пока по предыдущему ещё идут повторы (или даже пока идёт само заучивание). При создании нового плана бот предупреждает, если он накладывается на активный, и показывает, сколько повторов уже запланировано на ближайшие дни.
- Повторы по старым текстам не прерываются при добавлении нового.
- В сообщениях всегда указывать, к какому тексту относится порция (название текста + номера строк).
- Список текстов с прогрессом — команда `/texts` (раздел 5.5).

## 5. Логика SRS-цепочки

**При отправке порции** создаётся `Portion` (`status = sent`, `sentAt = now`) и одна запись `Review` со `stage = learn_reminder`, `dueAt = sentAt + learnReminderDelayMin` (по умолчанию +2 часа).

**При нажатии «Выучил»** (`learnedAt = now`) `learn_reminder` отменяется (`cancelled`, если ещё не отправлено), вычисляется `anchorAt` — **ближайший** к `learnedAt` слот пользователя (основной или второй, в любую сторону; раздел 5.1), и создаются записи повторов:

| stage | сдвиг от `anchorAt` |
|---|---|
| rep_12h | +12 часов (следующий слот) |
| rep_1d | +1 сутки |
| rep_3d | +3 суток |
| rep_2w | +14 суток |
| rep_1m | +30 суток |

«+N суток» — тот же местный час N дней спустя (с учётом перехода на летнее время, luxon). Если слот `anchorAt + 12 ч` уже прошёл к моменту нажатия (anchor округлён назад), `rep_12h` получает `dueAt` = ближайший будущий слот.

Пока порция не отмечена «Выучил», повторов по ней нет — она только висит в долге как «выучить» (раздел 5.2).

- **«Напомнить позже»** — `learn_reminder` сдвигается на час (с учётом тихих часов).
- **«Ещё учу»** — `learn_reminder` отменяется, порция остаётся в долге, новая не приходит, пока не нажато «Выучил».
- После подтверждения `rep_1m` цепочка по порции закрывается — новых `Review` не создаётся, `Portion.status → 'completed'`. Когда все строки плана выданы и выучены — `Plan.status → learning_done`; когда все порции `completed` — `completed`.

Даты этапов считаются от `anchorAt`, а не от момента выполнения предыдущего этапа. Если повтор сделан с опозданием, следующие этапы не сдвигаются; если к моменту выполнения уже наступил и следующий этап — они просто объединяются в одну сводку (раздел 5.1). Невыполненный повтор не пропадает: он остаётся в долгах, пока пользователь его не отметит (раздел 5.2).

**Статусы `Review`:** `pending` (ещё не отправлен) → `sent` (попал в сообщение, `deliveryId` = это сообщение) → `confirmed`. Ответ «Не успел» → `missed`; такой повтор остаётся долгом и попадает в следующие напоминания (`deliveryId` перезаписывается последней отправкой). Долг = любой повтор с `dueAt <= now` и статусом не `confirmed`.

## 5.1. Сводные повторы — одно сообщение вместо нескольких

Пользователь не должен получать повторы отдельными сообщениями по каждой порции. Пример: выучил бейты 1–5 и 6–10 в разные дни, и в какой-то момент обе порции пора повторить — бот присылает **одно** сообщение «Повторить: бейты 1–10», а не два по пять.

**Слоты отправки.** У пользователя два слота в сутки: **основной** (`dailySendTime`, выбранное им время, например 06:00 или 20:00) и **второй** (+12 часов от основного). Так как `anchorAt` — всегда слот, а все сдвиги кратны 12 часам, все повторы попадают ровно в слоты: +12 ч — противоположный слот, +1 д / +3 д / +14 д / +30 д — тот же слот нужного дня.

**Тихие часы.** `dueAt` хранит логический слот. **Основной слот (`dailySendTime`) никогда не считается ночным**: это время пользователь выбрал сам, поэтому всё, что приходит в основной слот (новая порция, повторы +1д/+3д/+2нед/+1мес, сводка с долгом), отправляется ровно в него, даже если оно попадает в `nightStart–nightEnd`. Для остальных сообщений (второй слот +12 ч, вечернее напоминание, `learn_reminder`, «Напомнить позже», порция «сразу после закрытия долга») момент отправки = время по расписанию с учётом `nightPolicy`: при `move` сообщение, попадающее в `nightStart–nightEnd`, отправляется в `nightEnd`. Это чистая функция в `src/core/time`.

**Сборка сообщения.** В каждый слот планировщик по каждому тексту пользователя берёт повторы для отправки:
- во **второй слот** — только новые наступившие (`status = pending`, `dueAt <= now`);
- в **основной слот** — все наступившие неподтверждённые (`pending`, `sent`, `missed`) — это одновременно и сводный повтор, и напоминание о долге (раздел 5.2); если в долге есть невыученная порция — она тоже входит.

Для каждого текста:
1. объединяет диапазоны строк всех этих повторов, сливая соседние и пересекающиеся (1–5 + 6–10 → 1–10; 1–5 + 16–20 → «1–5, 16–20»);
2. отправляет картинки строк по порядку (одна — `sendPhoto`, несколько страниц — альбом, больше 10 картинок — несколько альбомов подряд), затем **одно текстовое сообщение с кнопками**: «Повторение: <название текста>, бейты 1–10, 16–20» и «Повторил» / «Не успел»;
3. создаёт `Delivery (kind = review_batch)` с уникальным ключом слота, привязывает к нему все вошедшие `Review` (`status = sent`). Ответ ставит статус всем повторам этой отправки сразу, кнопки у сообщения убираются (`editMessageReplyMarkup`).

Нажатие кнопки под **старым** сообщением подтверждает только те повторы этой отправки, которые ещё не подтверждены; повторное нажатие ничего не ломает (идемпотентно).

Для нескольких текстов у одного пользователя — по одному сводному сообщению на текст в этом слоте (у каждого текста свои картинки и свои кнопки).

**Что остаётся отдельным:** новая порция приходит своим сообщением с кнопками «Выучил» / «Ещё учу» / «Напомнить позже». Объединяются только повторы (и долг в напоминаниях, раздел 5.2).

Второй строкой под этими кнопками идут кнопки контекста — «Захватить больше», «Ещё выше», «Ещё ниже» (раздел 4.1, «Показать больше контекста»). Они только досылают картинки и на SRS не влияют.

**Если повторов накопилось много** (например, после перерыва) — всё равно одно сводное сообщение на текст; при большом числе картинок — несколько альбомов подряд, кнопки — одним сообщением в конце.

Логику объединения диапазонов, округления до ближайшего слота и применения тихих часов писать чистыми функциями в `src/core/srs` и покрыть юнит-тестами (соседние, пересекающиеся, несмежные диапазоны; «Выучил» между слотами — округление вперёд и назад; тихие часы keep/move; смена часового пояса; переход на летнее время).

## 5.2. Строгий режим: новая порция только после выполненных повторов

Цель: не дать человеку копить невыполненные повторы, пока идут новые порции (так заучивание обычно и бросают).

**Долг** по тексту — это всё, что пора было сделать и что не отмечено:
- повторы (`Review`, кроме `learn_reminder`) с `dueAt <= now` и статусом не `confirmed` (не пришедшие, отправленные без ответа, с ответом «Не успел»);
- последняя выданная новая порция, по которой не нажато «Выучил».

Долг считается **по каждому тексту отдельно**: невыполненные повторы текста A останавливают новые порции только текста A.

**Плановые сутки** — интервал от основного слота одного дня до основного слота следующего дня (по местному времени пользователя). По одному тексту выдаётся **не больше одной новой порции за плановые сутки**.

**Правило выдачи новой порции:**
- в основной слот рабочего дня: долга нет и порция в эти плановые сутки ещё не выдавалась → выдаётся следующая порция плана (`Plan.nextLine`, `unitsPerDay` строк);
- долг есть → новая порция **не выдаётся**; вместо неё приходит сводное сообщение с долгом (раздел 5.1).

**Цикл напоминаний о долге:**
1. **Конец дня** (`eveningReminderTime`, по умолчанию 21:00, настраивается). Напоминание срабатывает в эти плановые сутки, только если оно отстоит **не меньше чем на 3 часа** и от текущего, и от следующего основного слота; иначе в эти сутки пропускается. Если долг есть — одно сообщение на текст «Сегодня не выполнено: повторить бейты …; выучить бейты …» с картинками (объединёнными, как в разделе 5.1).
2. **Следующий основной слот**: если долг остался — то же сообщение повторяется, новая порция не выдаётся. Туда же добавляются повторы, которые наступили с тех пор, — всё в одном сообщении.
3. **Кнопки в сообщении о долге:** «Выучил бейты X–Y» (только если в долге есть невыученная порция; нажатие запускает цепочку повторов по разделу 5), «Повторил(а) всё» (подтверждает все повторы этого сообщения), «Не успел(а)».
4. **Закрытие долга** — когда подтверждены все наступившие повторы и выучена порция. Тогда (правило **«выдать сейчас или в слот»**, общее для первой порции плана и порции после закрытия долга):
   - сейчас рабочий день, порция в эти плановые сутки ещё не выдавалась и сейчас раньше порога (момент `eveningReminderTime` этих суток; если вечернее напоминание в эти сутки не срабатывает — за 3 часа до следующего основного слота) → новая порция приходит **сразу**;
   - иначе → в следующий основной слот рабочего дня.

**Сроки плана.** Пользователь указал срок, поэтому при задержке бот не молча сдвигает дату, а после закрытия долга (если отставание ≥ 1 порции) предлагает выбор:
- «Успеть к сроку» — оставшиеся строки перераспределяются на оставшиеся рабочие дни (норма в день растёт; бот показывает новую норму);
- «Сдвинуть срок» — норма прежняя, дата окончания переносится (бот показывает новую дату, `Plan.estimatedEndDate`).
Если до срока осталось слишком мало дней для разумной нормы (норма выросла более чем вдвое) — бот советует сдвинуть срок. Порции идут строго по порядку, пропусков не бывает. В режиме «по строкам в день» дата просто сдвигается, бот сообщает новую.

**Защита от спама:**
- долг по тексту не закрывается 3 плановых суток подряд → по этому тексту **одно сообщение в сутки** (сводка с долгом в основной слот); второй слот, вечернее напоминание и `learn_reminder` по нему не отправляются;
- пользователь **7 дней не нажал ни одной кнопки и не отправил ни одной команды** (`User.lastActivityAt`) → автоматическая пауза на уровне пользователя (те же поля, что «пока сам не продолжу», раздел 5.5) с сообщением «План на паузе. Нажми «Продолжить», когда будешь готов»; при продолжении первым делом приходит сводный повтор всего долга.

Логику «есть ли долг», «что входит в напоминание», «когда выдавать следующую порцию», «срабатывает ли вечернее напоминание» писать чистыми функциями в `src/core/` и покрыть юнит-тестами: долг закрыт до порога → порция сразу; после → в следующий основной слот; порция уже выдана в эти сутки → не выдаётся; выходной; долг не закрыт → повторное напоминание с добавлением новых повторов; вечернее напоминание при основном слоте 06:00 / 20:00 / 22:00; 3 суток долга и 7 дней без активности; пересчёт нормы «успеть к сроку».

## 5.3. Создание плана: темп, выходные, расчёт нагрузки

**Шаг 1. Что учить** — весь файл (по умолчанию) или диапазон строк.

**Шаг 2. Способ задать темп** — пользователь сам выбирает один из двух (кнопки):

- **«По сроку»** → срок задаётся одним из способов: «Количество дней» (N), «Количество месяцев» (M × 30 дней), «К дате» (`ДД.ММ.ГГГГ`, с подсказками «через месяц / 3 месяца / полгода / год»). Бот сам считает, сколько строк в день.
- **«По количеству строк в день»** → пользователь вводит число строк в день; бот сам считает дату окончания. Перед вводом бот показывает рекомендацию: «Обычно по силам 2–5 строк в день» (кнопки 2 / 3 / 5 + свой вариант).

Дата начала по умолчанию — сегодня; можно указать другую («с 1 октября»). Первая порция после «Начать» приходит по правилу «выдать сейчас или в слот» (раздел 5.2); если дата начала в будущем — в основной слот этой даты (или ближайшего рабочего дня после неё). Месяц = 30 дней. Все интервалы дат — включительно (дата начала и дата окончания — рабочие дни плана, если не выходные).

**Шаг 3. Выходные** — пользователь может выбрать **до двух дней недели** без занятий (кнопки дней недели, выбор 0–2; третий выбрать нельзя). В выходной день **не приходит только новая порция**. Повторы приходят как обычно (по своим датам и слотам, интервалы не сдвигаются), напоминания о долге по повторам — тоже. Выходной не считается пропуском и не сдвигает план сверх заложенного в расчёт. Если долг закрыт в выходной, новая порция придёт в основной слот следующего рабочего дня.

**Расчёт** (чистые функции в `src/core/plan`):
- рабочие дни = дни от даты начала до даты окончания включительно без выбранных выходных;
- режим «по сроку»: `units_per_day = ceil(total_units / рабочие_дни)`; дата окончания = указанная пользователем; если строк меньше, чем рабочих дней, — по одной строке в день, план закончится раньше срока (сообщить);
- режим «по строкам в день»: `рабочие_дни = ceil(total_units / units_per_day)`; дата окончания = дата последнего рабочего дня;
- последняя порция может быть короче;
- нагрузка на повторы: по календарю плана (с учётом выходных; предполагая, что каждая порция выучена в день выдачи) посчитать, сколько строк придётся повторять в каждый день → показать «обычно ~N строк повтора в день, на пике до ~M»;
- даты: окончание заучивания и последние повторы (дата выдачи последней порции + 30 дней).

**Предупреждение о перегрузке** (мягкое, не запрещает):
Если новых строк в день больше 10 или повтор на пике больше 50 строк (пороги — в конфиге), бот показывает окно: «Это может оказаться тяжело: каждый день N новых строк и до M строк повтора. Рекомендуем 2–5 строк в день.» Кнопки: «Уменьшить нагрузку» (вернуться к выбору темпа) / «Всё равно продолжить». Решение остаётся за пользователем.

**Подтверждение** — одно сообщение, например:
«Файл: منظومة في أحكام الفقه, бейты 1–448. Темп: 5 бейтов в день. Выходные: пятница. Заучивание закончится 30.12.2026, последние повторы — 29.01.2027. Повторение: обычно 15–25 бейтов в день. Новая порция — в 06:00, повтор через 12 часов — в 18:00, напоминание о невыполненном — в 21:00.» Кнопки: «Начать» / «Изменить темп» / «Изменить выходные» / «Изменить дату начала» / «Изменить время».

При пересчёте из-за задержек (раздел 5.2) выходные тоже учитываются.

## 5.4. Первый запуск, часовой пояс и время отправки

1. `/start` → приветствие и выбор **часового пояса кнопками «город + смещение от UTC»** — например «Москва +3», «Екатеринбург +5» (город текстом не вводится, геолокация не запрашивается). Страницы кнопок: «Россия» (по умолчанию, 11 поясов от Калининграда до Камчатки), «СНГ и другие страны» (Минск, Киев, Стамбул, Эр-Рияд, Каир, Дубай, Баку, Тегеран, Ташкент, Алматы, Бишкек, Берлин, Лондон, Нью-Йорк), «Нет моего города» (просто UTC−12…+14). За кнопкой — IANA-пояс города (`Asia/Yekaterinburg`), поэтому смещение на кнопке считается на текущую дату и переход на летнее время учитывается автоматически. После выбора бот показывает пояс и текущие местные дату и время: «Да, верно» / «Выбрать другой». Хранится только IANA-пояс.
2. Вопрос о времени новой порции — **любое время по выбору пользователя** (кнопки с популярными вариантами + ввод `ЧЧ:ММ`).
3. Бот сразу показывает расписание, которое из этого следует: «Новая порция — в 14:00. Повтор через 12 часов — в 02:00 ночи. Остальные повторы — в 14:00. Напоминание о невыполненном — в 21:00.»
4. Если повтор через 12 часов или напоминание о невыполненном попадает в тихие часы (по умолчанию 23:00–07:00; выбранное время новой порции ночным не считается никогда — раздел 5.1), бот об этом говорит и предлагает выбор: «Оставить по часам» (`nightPolicy = keep`) или «Переносить ночные на утро» (`nightPolicy = move`, сообщение приходит в `nightEnd`, по умолчанию 07:00; утро можно изменить). Политика действует на все виды сообщений.
5. Если пользователь присылает PDF до завершения онбординга — бот сохраняет файл и сначала завершает онбординг, затем продолжает с разбором.
6. Всё это можно поменять позже в `/settings` (часовой пояс, время, тихие часы, политика ночных, время напоминания о невыполненном). При смене времени/пояса будущие `dueAt` пересчитываются: `anchorAt` округляется к новым слотам, от него заново считаются неподтверждённые будущие этапы.

## 5.5. Управление: пауза, настройки, удаление, команды

**Пауза** (`/pause` или «Настройки → Пауза»):
- варианты длительности кнопками: 1 день, 1 неделя, 2 недели, 3 недели, 1 месяц, «до даты…», «пока сам не продолжу»;
- пауза действует на все тексты пользователя;
- во время паузы не приходит ничего: ни новых порций, ни повторов, ни напоминаний о долге; `dueAt` повторов не сдвигаются;
- при постановке бот подтверждает: «Пауза до 22.09.2026. Продолжим в 06:00 22.09»; под сообщением — «Продолжить сейчас»;
- за день до окончания паузы (если пауза дольше 2 дней) — предупреждение «Завтра продолжаем»;
- после окончания (или «Продолжить сейчас»): первым делом — одно сводное сообщение со всеми повторами, которые наступили за время паузы и до неё не были сделаны (раздел 5.1); новая порция — только после его выполнения (строгий режим 5.2);
- срок плана автоматически сдвигается на длительность паузы (в режиме «по сроку» тоже), бот сообщает новую дату окончания;
- автопауза из раздела 5.2 (7 дней без активности) использует те же поля, как «пока сам не продолжу».

**Настройки** (`/settings`), каждое изменение — с подтверждением и показом нового расписания:
- часовой пояс;
- время новой порции;
- тихие часы и политика ночных сообщений (по часам / на утро);
- время напоминания о невыполненном;
- через сколько напоминать про неотмеченную порцию;
- выходные (0–2 дня);
- темп по конкретному тексту: переключить «по сроку» ↔ «по строкам в день», изменить срок или число строк в день — меняется расчёт только **ещё не выданных** строк; уже выданные порции и их повторы не трогаются; бот показывает новую норму/дату и нагрузку (с тем же мягким предупреждением, что в 5.3);
- удалить один текст (план, порции, повторы, файл, кэш картинок);
- **удалить все мои данные** — двойное подтверждение («Точно удалить? Это нельзя отменить»), затем удаляются пользователь, все тексты, PDF-файлы, кэш картинок, планы и история; бот отвечает, что данные удалены и можно начать заново через `/start`.

При смене часового пояса/времени/выходных будущие `dueAt` пересчитываются по новым слотам (чистая функция + тесты).

**Команды** (зарегистрировать через `setMyCommands`, чтобы они были в меню Telegram):

| команда | что делает |
|---|---|
| `/start` | первый запуск (раздел 5.4) или приветствие и краткая сводка, если пользователь уже есть |
| `/today` | что на сегодня: новая порция (выдана / ждёт / заблокирована долгом), повторы на сегодня, долг — с кнопками открыть картинки и отметить |
| `/progress` | прогресс по каждому тексту: выучено строк из N, %, текущий темп, дата окончания, сделано/пропущено повторов, серия дней без долгов |
| `/texts` | список текстов с кратким прогрессом; у каждого — «Открыть план», «Изменить темп», «Удалить»; кнопка «Загрузить новый текст» |
| `/pause` | поставить паузу или продолжить (если пауза уже стоит) |
| `/settings` | все настройки из списка выше, включая удаление данных |
| `/help` | как пользоваться ботом: как загрузить PDF, как работают повторы и строгий режим, выходные, пауза, список команд |

Все тексты интерфейса — на русском, в одном файле (`src/delivery/bot/texts.ts`), чтобы позже было легко добавить другие языки.

## 5.6. Надёжность планировщика

- **Тик раз в минуту**, один на процесс; на время тика берётся `pg_try_advisory_lock` — если запущен второй экземпляр или предыдущий тик не закончился, новый тик пропускается.
- **Атомарные переходы статусов**: запись берётся в работу через `UPDATE … WHERE status = 'pending' … RETURNING` (или `SELECT … FOR UPDATE SKIP LOCKED`); `Delivery` с уникальным `dedupeKey` (пользователь + текст + вид + слот) создаётся до отправки (`status = sending`) — повторная попытка того же слота упирается в уникальность и не шлёт дубль.
- **Ошибки отправки**: 429/5xx — повтор через `auto-retry`; иная ошибка — запись возвращается в `pending` и будет взята следующим тиком (с логом). 403 (бот заблокирован) → `User.blockedAt`, рассылка этому пользователю прекращается до следующего `/start`.
- **Догон после простоя**: при старте и на каждом тике обрабатывается всё, что созрело, но каждый пропущенный слот отправляется **один раз** (последний прошедший), а не по разу за каждый пропущенный. Если основной слот прошёл, а порция не выдана — она выдаётся по правилу «выдать сейчас или в слот» (раздел 5.2).
- **Лимиты Telegram**: троттлинг исходящих (≈ до 30 сообщений в секунду суммарно), альбомы — не чаще раза в несколько секунд одному пользователю.
- **Graceful shutdown**: на SIGTERM остановить polling и cron, дождаться окончания текущего тика, закрыть Prisma.
- **Время**: в БД всё хранится в UTC; местное время, слоты, выходные и переход на летнее время — только через luxon в чистых функциях.

## 5.7. Лимиты и доступ

- Бот **публичный** — написать ему может любой пользователь Telegram.
- PDF — не больше **20 МБ** (ограничение Bot API на скачивание файлов) и не больше **500 страниц**; текст из картинок — не больше **300 картинок**. Лимит страниц — собственный, а не Telegram: он защищает очередь разбора (рендер для анализа ≈ 0,2 с на страницу, `متن عمدة الاحكام.pdf` — 267 страниц за 50 с). Страницы рендерятся для анализа частями по 50 (`limits.pdf.renderChunkPages`), таймаут — на часть, файлы части удаляются сразу после анализа.
- Не больше **10 текстов** на пользователя; **один активный план** на текст.
- Повторная загрузка того же файла (одинаковый `sha256`) — не создаёт новый текст, бот предлагает открыть существующий.
- Разборы PDF выполняются последовательно (очередь), пользователю показывается его место/статус.
- Все пороги — в конфиге (`src/config`), не в коде обработчиков.
- Персональных данных хранить минимум (telegram id, username, часовой пояс; город не хранится) — сервер вне РФ, учитывать 152-ФЗ.

## 8. Definition of Done для MVP

- Можно отправить боту PDF, получить сводку по распознанным строкам, подтвердить, задать объём и срок, получить план.
- В указанное время приходит порция на день (картинками, кнопки — отдельным сообщением при альбоме).
- Под новой порцией есть кнопка «Выучил»; если не нажата — через 2 часа приходит одно напоминание.
- Пока есть невыполненные повторы или неотмеченная порция — новая порция по этому тексту не приходит; вечером и в основной слот приходят напоминания о долгах; после их закрытия новая порция приходит по правилам раздела 5.2; больше одной новой порции за плановые сутки не приходит.
- Через 12ч/1д/3д/14д/30д после «Выучил» (с округлением до слота) приходят повторы; все повторы одного слота по одному тексту приходят одним сообщением с объединёнными диапазонами и одним вопросом.
- После повтора "+1 месяц" порция больше не напоминает о себе.
- Все запланированные напоминания переживают перезапуск процесса бота (хранятся в БД, не в памяти), дублей после перезапуска нет.
- Пауза на выбранный срок работает: ничего не приходит, после окончания — сводный повтор, срок плана сдвинут.
- В `/settings` можно сменить часовой пояс, время, темп, выходные и удалить все данные; команды `/today`, `/progress`, `/texts`, `/pause`, `/settings`, `/help` есть в меню и работают.
- Юнит-тесты на расчёт нормы, дат повторов, слотов и правил строгого режима — зелёные; эталонный PDF разбирается в 448 строк.
