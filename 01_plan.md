# ALMATN — план разработки Telegram-бота для заучивания текстов

Проект: **almatn**. Бот принимает любой PDF (например, манзуму на арабском с пронумерованными строками), спрашивает объём и темп заучивания, рассчитывает дневную норму, присылает порции по расписанию (картинками, вырезанными из PDF) с кнопкой «Выучил», и ведёт каждую выученную порцию по схеме интервального повторения: **+12 часов → +1 сутки → +3 суток → +2 недели → +1 месяц (30 дней)**, отсчитанной от момента «Выучил», после чего порция считается закрытой. Повторы приходят одним сводным сообщением, а новая порция выдаётся только после выполнения всех повторов (строгий режим).

Полное ТЗ — [CLAUDE.md](./CLAUDE.md). Этот файл — обзор и порядок работ; при расхождении прав CLAUDE.md.

## 1. Архитектурное решение

Делаем **чистого Telegram-бота** как MVP, но архитектуру строим так, чтобы позже добавить **Telegram Mini App** (веб-интерфейс внутри Telegram) без переписывания логики. Достигается это разделением на слои:

```
almatn/
  src/
    core/              # вся бизнес-логика, НЕ знает о Telegram и БД
      pdf/             # разбор PDF → строки с координатами; вырезка картинок порций
      plan/            # расчёт дневной нормы, календаря плана и нагрузки
      srs/             # расчёт дат повторов, слоты, объединение диапазонов
      scheduler/       # поиск "созревших" задач и их обработка
    delivery/
      bot/             # обработчики команд/кнопок Telegram (использует core/)
      api/             # ПОЯВИТСЯ на этапе Mini App: REST + Telegram WebApp auth
    db/
      repositories/    # доступ к данным через Prisma, общий для bot/ и будущего api/
    config/
  webapp/              # ПОЯВИТСЯ на этапе Mini App (React/Vite фронтенд)
  prisma/
    schema.prisma
  CLAUDE.md
  .env.example
  package.json
```

Ключевое правило: **ни один обработчик бота не содержит бизнес-логики напрямую** — он только вызывает функции из `core/` и репозитории и оборачивает результат в Telegram-сообщение. Когда появится Mini App, `delivery/api/` будет вызывать те же самые функции `core/`, отдавая JSON вместо сообщений. Уведомления в любом случае всегда идут через Bot API — Mini App сам по себе слать пуши не может, он только открывается по кнопке и показывает порции/прогресс.

Идентификатор пользователя везде один — `telegram_id`, поэтому авторизация в будущем Mini App (через `Telegram.WebApp.initData`) сведётся к тому же ID, что и в боте, без отдельной регистрации.

## 2. Технологический стек

- **Node.js + TypeScript**, ESLint + Prettier, **vitest** для тестов
- **grammY** + `@grammyjs/auto-retry` и троттлинг — соблюдение лимитов Telegram
- **PostgreSQL + Prisma ORM** — миграции (`prisma migrate dev` локально, `prisma migrate deploy` на сервере)
- **luxon** — часовые пояса и слоты; **zod** — проверка `.env`; **pino** — логи
- **Планировщик**: без Redis/BullMQ — "таблица задач + опрос раз в минуту" (`node-cron`), в том же процессе, что и бот; защита от двойной отправки — атомарные переходы статусов и advisory lock (CLAUDE.md, раздел 5.6)
- **PDF**: poppler — `pdftotext -bbox` (слова с координатами), `pdftoppm` (рендер страниц); `sharp` — обрезка и анализ пикселей; разбор — в дочернем процессе, не в основном потоке; порции отправляются картинками. OCR не используется
- **Хостинг**: VPS, **Docker Compose** (бот + Postgres, poppler в образе), long polling (без HTTPS-домена); вебхук — опционально позже

**Важный нюанс**: пользователь в РФ. Telegram Bot API из России может работать нестабильно. Рекомендуется размещать бота на VPS **вне РФ** (Европа — Германия/Нидерланды и т.п.). Учитывать 152-ФЗ: хранить минимум персональных данных.

## 3. Модель данных (кратко — подробности в CLAUDE.md, раздел 4)

- `users` — telegram_id, часовой пояс, время основного слота, тихие часы, пауза, признак блокировки бота
- `texts` — загруженный PDF (путь, sha256), название, единица («строки»/«бейты»), стратегия разбора
- `lines` — строки: итоговый и напечатанный номер, страница, координаты (текст не хранится)
- `plans` — диапазон, темп (по сроку / строк в день), выходные, статус; один активный план на текст
- `portions` — выданный диапазон строк; создаётся **в момент выдачи**, хранит время отправки и «Выучил»
- `reviews` — повторы `rep_12h … rep_1m` и `learn_reminder` со статусом и `due_at`
- `deliveries` — журнал отправленных сообщений (порция, сводный повтор, напоминание о долге, …) с уникальным ключом «пользователь + текст + вид + слот» — защита от дублей после перезапуска

## 4. Этапы разработки (совпадают с CLAUDE.md, раздел 6)

### Этап 0. Подготовка (владелец)
- Создать **тестового** бота через @BotFather для разработки (боевой — отдельно, только на сервере)
- Установить Postgres и poppler, создать БД, заполнить `.env`
- Определиться с VPS вне РФ и местом для бэкапов

### Этап 1. Каркас проекта
- TypeScript, ESLint/Prettier, vitest, pino, zod-конфиг
- Prisma + Postgres, первая миграция
- Бот-заглушка на grammY: `/start`, `setMyCommands`

### Этап 2. Первый запуск
- Часовой пояс — кнопками «город + смещение» («Москва +3», «Екатеринбург +5»), страница «Нет моего города» — UTC±N; время новой порции (любое)
- Показ расписания, выбор для ночных сообщений — «оставить по часам» или «переносить на утро»

### Этап 3. Приём и разбор PDF
- Хэндлер документа; лимиты (≤ 20 МБ, ≤ 300 страниц, ≤ 10 текстов), дубли по sha256, понятные ошибки для кривых PDF
- Разбор: по напечатанным номерам (разные форматы и цифры, исправление опечаток) → по строкам текстового слоя → по изображению → ручной режим
- Сводка с картинкой первых строк: «Всё верно» / «Разобрать по-другому» / «Отмена»; название текста и единица «строки»/«бейты»
- Вырезка порций картинками; сохранение `texts` + `lines`

### Этап 4. Создание плана
- Что учить (весь файл или диапазон); темп — по сроку (дни, месяцы по 30 дней, дата) или строк в день (рекомендация 2–5); выходные — до двух дней
- Расчёт нормы, календаря и нагрузки на повторы, мягкое предупреждение о перегрузке, подтверждение
- Предупреждение о наложении на активные планы

### Этап 5. Планировщик и выдача порций
- Cron раз в минуту; порция в основной слот, если по тексту нет долга; первая порция и порция после закрытия долга — сразу, если рабочий день и раньше вечернего напоминания; не больше одной новой порции на текст за плановые сутки
- Кнопки «Выучил» / «Ещё учу» / «Напомнить позже»; `learn_reminder` через 2 часа
- По «Выучил» — цепочка повторов `+12ч, +1д, +3д, +2нед, +30д` от момента «Выучил», округлённого до ближайшего слота (основной или +12 ч)

### Этап 6. Сводные повторы и долги
- В каждый слот — одно сводное сообщение на текст с объединёнными диапазонами; кнопки «Повторил» / «Не успел» отдельным сообщением после альбома
- Напоминание о долге вечером и в основной слот; кнопки «Выучил бейты X–Y» (если нужно) и «Повторил(а) всё» / «Не успел(а)»
- Защита от спама (3 дня — одно сообщение в день, 7 дней без нажатий — автопауза); пересчёт «успеть к сроку» / «сдвинуть срок»

### Этап 7. Управление и команды
- Пауза: день, неделя, 2 и 3 недели, месяц, до даты, до ручного продолжения; после — сводный повтор, срок сдвигается
- `/settings`: часовой пояс, время, тихие часы, вечернее напоминание, выходные, темп, удаление текста и всех данных
- Команды в меню: `/today`, `/progress`, `/texts`, `/pause`, `/settings`, `/help`

### Этап 8. Тестирование (сквозное, по ходу всех этапов)
- Юнит-тесты на `core/plan`, `core/srs`, строгий режим, разбор эталонного PDF — пишутся вместе с кодом каждого этапа
- Ручное тестирование сценария целиком на тестовом боте

### Этап 9. Деплой
- Docker Compose на VPS вне РФ, `prisma migrate deploy` при старте, автоперезапуск
- Graceful shutdown (остановить polling, дождаться текущего тика), логи pino (опционально Sentry)
- Ежедневный бэкап БД **и** каталога с PDF, хранение копий вне этого VPS; инструкция по восстановлению

### Этап 10 (вторым релизом, вне MVP). Telegram Mini App
- `webapp/` — React/Vite: просмотр текущей порции (картинки из PDF), страница прогресса/статистики
- `delivery/api/` — Fastify-эндпоинты поверх тех же `core/`-функций, авторизация через `Telegram.WebApp.initData`
- Кнопка «Открыть в приложении» под сообщениями бота

## 5. Принятые решения

1. **Точка отсчёта повторов** — момент нажатия «Выучил», округлённый до ближайшего слота (основной или +12 ч). Пока порция не выучена, повторов по ней нет.
2. **Строгий режим:** пока не выполнены повторы и не отмечена последняя порция, новая порция по этому тексту не выдаётся. Долг считается **по каждому тексту отдельно**. Вечером приходит напоминание о долге, в основной слот оно повторяется (CLAUDE.md, раздел 5.2).
3. **Выдача новой порции:** не больше одной на текст за плановые сутки; первая порция и порция после закрытия долга — сразу, если сейчас рабочий день и раньше вечернего напоминания, иначе в следующий основной слот.
4. **Часовой пояс и время** — при первом запуске кнопки «город + смещение» («Москва +3») и любое время; ночные сообщения — по выбору: по часам или на утро; основной слот (выбранное пользователем время) ночным никогда не считается (CLAUDE.md, разделы 5.1, 5.4).
5. **Надёжность планировщика** — все события хранятся в БД (`due_at`, журнал отправок), без `setTimeout`; защита от дублей и догон после простоя (CLAUDE.md, раздел 5.6).
6. **Бот публичный с лимитами:** PDF ≤ 20 МБ (ограничение Bot API на скачивание) и ≤ 300 страниц, ≤ 10 текстов на пользователя, один активный план на текст (CLAUDE.md, раздел 5.7).
7. **Сканы** разбираются по изображению страницы, OCR не используется: порции — картинки, текст извлекать не нужно.
8. **Один процесс** для бота и планировщика; деплой — Docker Compose.
