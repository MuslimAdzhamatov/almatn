# ALMATN — план разработки Telegram-бота для заучивания текстов

Проект: **almatn**. Бот принимает PDF с пронумерованными строками (манзума на арабском и т.п.), спрашивает объём и срок заучивания, рассчитывает дневную норму, присылает её по расписанию, через час проверяет "выучил/повторил", и ведёт каждую порцию по схеме интервального повторения: **+12 часов → +1 сутки → +3 суток → +2 недели → +1 месяц**, после чего порция считается закрытой.

---

## 1. Архитектурное решение

Делаем **чистого Telegram-бота** как MVP, но архитектуру строим так, чтобы позже добавить **Telegram Mini App** (веб-интерфейс внутри Telegram) без переписывания логики. Достигается это разделением на слои:

```
almatn/
  src/
    core/              # вся бизнес-логика, НЕ знает о Telegram
      pdf/             # парсинг PDF → пронумерованные строки
      plan/            # расчёт дневной нормы по объёму и сроку
      srs/             # spaced-repetition движок (расчёт дат повторов)
      scheduler/        # поиск "созревших" задач и их выполнение
    delivery/
      bot/             # обработчики команд/кнопок Telegram (использует core/)
      api/             # ПОЯВИТСЯ на этапе Mini App: REST + Telegram WebApp auth
    db/
      schema.prisma
      repositories/    # доступ к данным, общий для bot/ и будущего api/
    config/
  webapp/              # ПОЯВИТСЯ на этапе Mini App (React/Vite фронтенд)
  prisma/
  CLAUDE.md
  .env.example
  package.json
```

Ключевое правило: **ни один обработчик бота не содержит бизнес-логики напрямую** — он только вызывает функции из `core/` и оборачивает результат в Telegram-сообщение. Когда появится Mini App, `delivery/api/` будет вызывать те же самые функции `core/`, отдавая JSON вместо сообщений. Уведомления в любом случае всегда идут через Bot API (`sendMessage`) — Mini App сам по себе слать пуши не может, он только открывается по кнопке и красиво показывает текст/прогресс.

Идентификатор пользователя везде один — `telegram_id`, поэтому авторизация в будущем Mini App (через `Telegram.WebApp.initData`) сведётся к тому же ID, что и в боте, без отдельной регистрации.

## 2. Технологический стек (рекомендация)

- **Node.js + TypeScript**
- **grammY** — современный фреймворк для Telegram-ботов на TS (хорошо документирован, поддерживает inline-кнопки, файлы, а также имеет плагины под Mini Apps на будущее)
- **PostgreSQL + Prisma ORM** — миграции, типобезопасные запросы, легко переиспользовать в будущем API
- **Планировщик**: без Redis/BullMQ на старте — простая и надёжная схема "таблица задач + опрос раз в 1–5 минут" (см. раздел 5). Это проще в хостинге и достаточно для объёмов одного бота. Redis/BullMQ — опция для масштабирования позже.
- **PDF**: координаты номеров бейтов (`pdfjs-dist` или poppler `pdftotext -bbox`) + рендер страниц (`pdftoppm`) + обрезка (`sharp`); порции отправляются картинками
- **Хостинг**: обычный VPS (Node-процесс + Postgres), long polling для старта (без необходимости в HTTPS-домене); вебхук — опционально позже

**Важный нюанс**: пользователь в РФ. Telegram Bot API из России может работать нестабильно. Рекомендуется размещать бота на VPS **вне РФ** (Европа — Германия/Нидерланды и т.п.), это снимает вопрос с доступностью API и не требует прокси.

## 3. Модель данных (кратко — подробности в CLAUDE.md)

- `users` — telegram_id, часовой пояс, время ежедневной рассылки
- `texts` — загруженный PDF, метаданные, общее число строк
- `lines` — строки текста с номерами (result парсинга PDF)
- `plans` — сколько учить, за сколько дней, норма в день, статус
- `portions` — конкретный кусок текста на конкретный день (диапазон строк)
- `reviews` — события напоминаний по каждой порции: `check_1h`, `rep_12h`, `rep_1d`, `rep_3d`, `rep_2w`, `rep_1m`, со статусом `pending / sent / confirmed / missed` и временем `due_at`

## 4. Этапы разработки

### Этап 0. Подготовка
- Создать бота через **@BotFather**, получить токен
- Определиться с хостингом (VPS вне РФ)
- Инициализировать репозиторий в папке `almatn`, `git init`, `.gitignore`, `package.json`
- Положить в корень `CLAUDE.md` (техзадание, см. отдельный файл)

### Этап 1. Каркас проекта
- Настроить TypeScript, ESLint/Prettier
- Настроить Prisma + подключение к Postgres, накатить первую миграцию по схеме из раздела 3
- Поднять "hello world" бота на grammY (отвечает на `/start`)

### Этап 2. Приём и парсинг PDF
- Хэндлер на получение документа в чате
- Бот принимает любой PDF: разбор по напечатанным номерам (разные форматы и цифры, исправление опечаток нумерации), по строкам текстового слоя, по изображению (сканы), либо ручной режим — страница целиком
- Сводка с картинкой первых строк и кнопкой «Разобрать по-другому»
- Несколько текстов у одного пользователя: следующий можно добавить в любой момент, повторы по прошлым продолжаются
- Вырезка порций картинками из отрендеренных страниц (текстовый слой реальных PDF непригоден — см. CLAUDE.md, раздел 4.1)
- Сохранение `texts` + `lines` (страница и координаты каждого бейта) в БД
- Ответ пользователю: сводка (сколько строк найдено, первая/последняя строка) для проверки корректности распознавания

### Этап 3. Диалог планирования
- Вопрос: сколько строк/объём учить (весь текст или часть)
- Вопрос: за сколько дней
- Расчёт `units_per_day = ceil(total_units / days)`, создание `plans` + генерация всех `portions` на весь срок (диапазоны строк по дням)
- Подтверждение плана пользователю

### Этап 4. Планировщик и ежедневная рассылка
- Фоновый процесс (cron раз в 1–5 минут), который:
  - находит `portions`, чей день наступил и время рассылки подошло → отправляет текст порции, создаёт для неё событие `check_1h` (due через 1 час)
  - находит `reviews` с `due_at <= now` и `status = pending` → отправляет напоминание с кнопками, помечает `sent`
- Обработка нажатий инлайн-кнопок ("Выучил"/"Повторил", "Ещё нет") → обновление статуса `reviews`/`portions`

### Этап 5. Движок интервального повторения (SRS)
- При подтверждении заучивания порции (или по факту её отправки — нужно решить точку отсчёта, см. раздел 6) — генерация цепочки `reviews`: `+12ч, +1д, +3д, +2нед, +1мес` от дня заучивания
- После `+1мес` — порция помечается `completed`, новых повторов не создаётся

### Этап 6. Тестирование
- Юнит-тесты на `core/plan` (расчёт нормы) и `core/srs` (расчёт дат повторов) — это чистые функции, тестируются без БД и без Telegram
- Ручное тестирование сценария целиком на тестовом боте

### Этап 7. Деплой
- VPS, systemd/pm2 для процесса бота, отдельный процесс/тот же — для планировщика
- Резервное копирование БД (ежедневный дамп)
- Логирование ошибок (хотя бы в файл, идеально — Sentry)

### Этап 8 (опционально, вторым релизом). Telegram Mini App
- `webapp/` — простой React/Vite фронтенд: страница чтения текста с подсветкой текущей порции (удобная RTL-вёрстка для арабского), страница прогресса/статистики
- `delivery/api/` — Fastify-эндпоинты, использующие те же `core/`-функции, авторизация через `Telegram.WebApp.initData`
- Кнопка "Открыть в приложении" под ежедневным сообщением бота

## 5. Важные нюансы и решения, которые нужно принять

1. **Точка отсчёта для SRS-цепочки**: от момента отправки порции или от момента, когда пользователь подтвердил "выучил"? Рекомендация для MVP — от **дня отправки порции** (не ждём подтверждения, чтобы не ломать расписание, если пользователь забыл ответить). Подтверждения используются для самоконтроля и статистики, а не как блокирующее условие.
2. **Если пользователь ответил "ещё не выучил"** — в MVP не меняем расписание повторов, а просто логируем и мягко напоминаем ещё раз в течение дня. Более умная адаптация (сдвиг расписания) — доработка после MVP.
3. **Часовой пояс и время рассылки** — спросить у пользователя один раз при первом запуске (или взять дефолт, например 6:00 по его часовому поясу), хранить в `users`.
4. **Надёжность планировщика** — обязательно хранить все "due"-события в БД с `due_at`, а не в памяти процесса/`setTimeout` — иначе при перезапуске сервера все запланированные напоминания потеряются.
5. **OCR для сканов арабского текста** — заранее предупредить, что в MVP точность ограничена; в идеале просить пользователя присылать PDF с текстовым слоем (не скан).
